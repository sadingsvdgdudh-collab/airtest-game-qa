# 本地环境部署与复现

本文所有命令都从**项目根目录**执行，即包含 `pyproject.toml`、`scripts/`、`adapters/` 的 `airtest-game-qa/` 目录。以下按 macOS ARM64 和 Bash 编写；所有下载、SDK、游戏数据库、模拟器数据及日志放入 `$PWD/.local-runtime`，不依赖交付者机器上的绝对路径或私有凭据。

本文已核对现有脚本、安装属性、固定下载清单和用例标记；当前机器完成过真实运行。**没有在全新机器上按本文重新安装并复验全部步骤**，因此不把文档核对等同于全新环境验收。新部署产生的报告应另行保存，不能覆盖 `docs/evidence/` 中已有证据。

## 2. 安装框架与配置

```bash
python3.12 -m venv "$GAMEQA_WORK_DIR/python-env"

python -m pip install -r requirements-lock.txt
python -m pip install --no-deps -e .
```

`tests/` 是框架自检，单独统计，不当作真实游戏业务通过数量。项目根的 `config.local.toml` 已被忽略；它的 `bridge_cwd="."` 相对于配置文件所在目录解析，因此不要未经修改将它移动到 `.local-runtime/`。若移到其他位置，需将 `bridge_cwd` 改为项目根的绝对路径。

公开样例已经用 `sh adapters/stendhal_bridge/run.sh` 启动Stendhal桥，日志路径通过 `${GAMEQA_WORK_DIR}` / `${SHARDY_LOGS}` 展开。样例不保存密码。

## 3. 准备和启动 Stendhal

`--download-jdk` 下载的是固定的 macOS ARM64 JDK21；其他平台需自行提供兼容JDK并用 `--java /path/to/java`。准备脚本下载并校验官方1.49发行包、固定源码和TypeScript，编译Web客户端及仅绑定loopback的网络接入补丁；不会启动游戏，也不会重置已有数据库。

```bash
export STENDHAL_NODE="$GAMEQA_NODE"
python scripts/stendhal/setup.py --download-jdk --node /path/to/node
export JAVA_HOME="$GAMEQA_WORK_DIR/tools/zulu21.40.17-ca-jdk21.0.6-macosx_aarch64/zulu-21.jdk/Contents/Home"
export STENDHAL_JAVA="$JAVA_HOME/bin/java"
export STENDHAL_RUNTIME="$GAMEQA_WORK_DIR/stendhal/runtime"
export BRIDGE_BUILD_DIR="$GAMEQA_WORK_DIR/protocol-bridge/classes"
export PATH="$JAVA_HOME/bin:$PATH"
"$STENDHAL_JAVA" -version
sh adapters/stendhal_bridge/build.sh --install-probe
```

上面的 `/path/to/node` 与第一节同为 Node 24.19.0；也可写 `--node "$GAMEQA_NODE"`。安装测试助手应在服务器首次启动前完成；已经加载的助手不会因复制新class而热替换。管理员名单位于 `$STENDHAL_RUNTIME/data/conf/admins.txt`，准备脚本添加独立 `qaobserver`，不要把测试角色加入管理员名单。

在保留这些变量的终端启动主服，命令保持前台运行；在另一个配置相同环境的终端执行开户及测试：

```bash
sh scripts/stendhal/start.sh main
```

**停服与数据库**：停服前确认没有 `gameqa run` 在跑。`stop.sh` 会先看 `console.log` 里是否有
`DBCommandQueue has N entries`（说明还有写未落库），有就等 30 秒、再停，并最多等 90 秒让进程退出。
如果在写队列未排空时强停，会**丢写**：症状是之后主服报
`Trying to load a non active character` / `could not load object for character ... from database`，
**任何角色都登不进去**。恢复办法：停服 → 把 `runtime/database/` 整个移开留档 → 重启（世界由 XML 重建）
→ `python scripts/stendhal/bootstrap_accounts.py --config "$GAMEQA_CONFIG"` 重建三个账号角色。
世界重建后先静置一两分钟再跑用例（首跑时 H2 会集中落库，容易把连接挤断）。

主服监听 `127.0.0.1:32160`，Web/WS入口是 `http://127.0.0.1:8080/stendhal.html`。日志位于 `$STENDHAL_RUNTIME/log/server.log` 和 `console.log`，H2数据库在 `database/`。官方游戏源码保留GPL声明；Web初始化修复与受控注入分别记录，见[Stendhal接入说明](../integrations/stendhal/README.md)。

在Bash中静默输入自选本地测试密码，只导出环境变量，不写入公开配置：

```bash
read -rs -p "qaobserver 本地密码: " GAMEQA_OBSERVER_PASSWORD
printf '\n'
read -rs -p "测试玩家本地密码: " GAMEQA_PLAYER_PASSWORD
printf '\n'
export GAMEQA_OBSERVER_PASSWORD GAMEQA_PLAYER_PASSWORD
python scripts/stendhal/bootstrap_accounts.py --config "$GAMEQA_CONFIG"
```

脚本通过32160的真实协议创建或验证 `qaobserver`、`qaplayer`、`qaplayera` 三个账号和同名角色；两个玩家账号使用 `GAMEQA_PLAYER_PASSWORD`，管理员使用另一个变量。已有账号需输入其原密码，重复开户不会重置密码。原版账号名不能带数字。桥连接仅允许loopback本地测试服，不要替换成公共游戏地址。

### 两条硬约束（实测，别踩）

① **QaProbe 只接受 `qaobserver` 这一个管理员**：`QaProbe.java` 里是硬校验
（`admin == null || !admin.getName().equals("qaobserver") || admin.getAdminLevel() < 1000` 直接抛错），
所以**不要配置第二个观察者账号** —— 账号池/轮换方案在探针侧会被直接拒绝。
（账号轮换实验已验证：实测更差——冷账号放大"重复登录静默踢人"的竞态、单条用例 12s→40s，配置里 `pool_size` 保持 1。）

② **服务端会主动关闭静默约 10–15 秒的连接**（实测：静默 8 秒可用 / 15 秒被关 / 25 秒角色判定离线）。
桥侧保活（`keepalive_op` + `keepalive_interval`）能续命，但它依赖"**重连后能重启保活线程**"：
`Bridge._start()` 每次（重）启动都会重建 `_keepalive_stop` 并清空线程引用——改这段代码时别把这一步去掉。

## 4. 固定 Android SDK 和 AVD

当前默认SDK包会随官方更新。为复现本次工具版本，使用下面的固定Google下载包；其SHA1与本次已下载文件及[官方SDK包索引](https://dl.google.com/android/repository/repository2-3.xml)、[Google APIs镜像索引](https://dl.google.com/android/repository/sys-img/google_apis/sys-img2-1.xml)一致。这些包供首次安装到新隔离目录使用，不执行 `sdkmanager --update`。

```bash
export ANDROID_HOME="$GAMEQA_WORK_DIR/android/sdk"
source scripts/android/env.sh
export GAMEQA_ANDROID_DOWNLOADS="$GAMEQA_WORK_DIR/android/downloads"
mkdir -p "$GAMEQA_ANDROID_DOWNLOADS" "$ANDROID_HOME/cmdline-tools" \
  "$ANDROID_HOME/system-images/android-34/google_apis" \
  "$ANDROID_AVD_HOME" "$ANDROID_USER_HOME" "$GAMEQA_WORK_DIR/android/logs"
curl -fL https://dl.google.com/android/repository/commandlinetools-mac_arm64-16111833_latest.zip \
  -o "$GAMEQA_ANDROID_DOWNLOADS/cli.zip"
curl -fL https://dl.google.com/android/repository/platform-tools_r37.0.1-darwin.zip \
  -o "$GAMEQA_ANDROID_DOWNLOADS/platform-tools.zip"
curl -fL https://dl.google.com/android/repository/emulator-darwin_aarch64-16428233.zip \
  -o "$GAMEQA_ANDROID_DOWNLOADS/emulator.zip"
curl -fL https://dl.google.com/android/repository/sys-img/google_apis/arm64-v8a-34_r14.zip \
  -o "$GAMEQA_ANDROID_DOWNLOADS/image.zip"
(
  cd "$GAMEQA_ANDROID_DOWNLOADS"
  shasum -a 1 -c <<'SHA1'
ad03dc49bfacfd52c110b14104ea548b8a07e830  cli.zip
6ae73f4de6452dc57e62ec02b68eed92a4c21661  platform-tools.zip
3af4fe44ce82b3d88ae5678a53735f27ad729c15  emulator.zip
2fe8b46d419a3400e30f31b0152b241b50c8b99f  image.zip
SHA1
)
```

全部校验通过后解压。`cmdline-tools/latest` 是工具要求的目录布局，里面实际安装的是固定23.0版本，不表示跟随最新包。

```bash
unzip -q "$GAMEQA_ANDROID_DOWNLOADS/cli.zip" -d "$GAMEQA_ANDROID_DOWNLOADS/cli-unpacked"
mv "$GAMEQA_ANDROID_DOWNLOADS/cli-unpacked/cmdline-tools" "$ANDROID_HOME/cmdline-tools/latest"
unzip -q "$GAMEQA_ANDROID_DOWNLOADS/platform-tools.zip" -d "$ANDROID_HOME"
unzip -q "$GAMEQA_ANDROID_DOWNLOADS/emulator.zip" -d "$ANDROID_HOME"
unzip -q "$GAMEQA_ANDROID_DOWNLOADS/image.zip" -d "$ANDROID_HOME/system-images/android-34/google_apis"
cat "$ANDROID_HOME/cmdline-tools/latest/source.properties"
cat "$ANDROID_HOME/platform-tools/source.properties"
cat "$ANDROID_HOME/emulator/source.properties"
cat "$ANDROID_HOME/system-images/android-34/google_apis/arm64-v8a/source.properties"
```

核对属性与第一节一致，再创建固定名称的AVD。`avdmanager`包含在23.0工具包，仍用于本次流程；官方现已标记弃用并提供Android CLI替代，不能仅凭 `sdkmanager --version` 输出的CLI版本判断工具包版本。命令与目录约定参见[官方sdkmanager文档](https://developer.android.com/tools/sdkmanager)和[avdmanager文档](https://developer.android.com/tools/avdmanager)。

```bash
printf 'no\n' | avdmanager create avd \
  --name airtest_api34_arm64 \
  --package 'system-images;android-34;google_apis;arm64-v8a' \
  --device pixel_2 \
  --path "$ANDROID_AVD_HOME/airtest_api34_arm64.avd"
```

为保持物理显示配置与已有图像基线一致，在未启动AVD时设置以下字段：

```bash
python - <<'PY'
import os

values = {'hw.lcd.width': '720', 'hw.lcd.height': '1280', 'hw.lcd.density': '320',
          'hw.ramSize': '1536', 'hw.cpu.ncore': '2', 'hw.keyboard': 'no',
          'skin.name': '720x1280', 'skin.path': '_no_skin', 'showDeviceFrame': 'no'}
lines = [line for line in path.read_text().splitlines()
         if line.split('=', 1)[0].strip() not in values]
path.write_text('\n'.join(lines + [f'{k} = {v}' for k, v in values.items()]) + '\n')
PY
```

另一个终端设置同一隔离环境并执行连接。若提示未完成启动，等系统启动完成后再次执行：

```bash
source scripts/android/env.sh
```

## 5. 准备和启动 Shardy

pnpm安装到隔离工具目录，不改动游戏业务源码。准备脚本固定上游提交及依赖锁，使用 `--frozen-lockfile --ignore-scripts`，随后仅编译TypeScript，不执行会改写上游源码的格式化脚本。

```bash
npm install --prefix "$GAMEQA_WORK_DIR/tools/pnpm" pnpm@11.25.0
export SHARDY_NODE="$GAMEQA_NODE"
export SHARDY_PNPM="$GAMEQA_WORK_DIR/tools/pnpm/node_modules/.bin/pnpm"
test "$("$SHARDY_PNPM" --version)" = "11.25.0"
export SHARDY_WORK="$GAMEQA_WORK_DIR/shardy"
export SHARDY_VENDOR="$SHARDY_WORK/vendor/shardy-tictactoe"
export SHARDY_LOGS="$SHARDY_WORK/logs"
export SHARDY_PORT=3000
bash adapters/shardy_bridge/prepare.sh
"$SHARDY_NODE" adapters/shardy_bridge/start_backend.mjs \
  > "$SHARDY_LOGS/backend.log" 2>&1 &
echo "$!" > "$SHARDY_WORK/backend.pid"
"$SHARDY_NODE" integrations/shardy_client/server.mjs \
  > "$SHARDY_LOGS/client.log" 2>&1 &
echo "$!" > "$SHARDY_WORK/client.pid"
```

`SHARDY_WORK`仅供准备脚本使用；后端和桥还需要显式 `SHARDY_VENDOR`，日志需要 `SHARDY_LOGS`，不能只设置一个目录变量。后端监听 `127.0.0.1:3000`，项目展示客户端监听 `127.0.0.1:3001`。展示页WebSocket固定使用3000，UI基线不能只改变 `SHARDY_PORT`。该网页是本项目客户端，不代表官方Unity客户端覆盖；见[客户端说明](../integrations/shardy_client/README.md)。

Android连接脚本已经反向映射这两个端口。UI用例会自行打开Chrome、连接并匹配一个真实API对手；独立运行Shardy不需要Stendhal账号密码。

## 6. 精确执行基线和已知失败组

先确认主服、Shardy后端/展示页及Android都已准备。**顺序执行各组**：Stendhal API与UI共用管理员和商店NPC，两个UI组共用Chrome；不要并发抢占这些会话。

框架自检仅执行 `tests/`：

```bash
python -m pytest tests -q
```

当前Stendhal已实现26个API执行ID和6个UI执行ID，分别已有各组验证证据；目录仍有未接入设计。下面的命令选择全部已实现主游戏API及UI，不会选择Shardy已知失败组：

```bash
python -m gameqa run --config "$GAMEQA_CONFIG" \
  --game stendhal --kind api --rounds 5
python -m gameqa run --config "$GAMEQA_CONFIG" \
  --game stendhal --kind ui --rounds 5
```

若单独复核战斗及移动5条（含距离、取消攻击），用 `--game stendhal --module combat --kind api --rounds 5`；单例定位用 `--case ST-SHOP-API-001 --rounds 1`；真实战斗界面用 `--case ST-COMBAT-UI-001 --rounds 1`。这些命令按当前可执行用例选择，不表示73条设计条目全部实现或通过。

Shardy正常API基线4条（匹配、轮次、非法动作、横排胜利）与UI基线1条明确选 `core`：

```bash
python -m gameqa run --config "$GAMEQA_CONFIG" \
  --game shardy --module core --kind api --rounds 5
python -m gameqa run --config "$GAMEQA_CONFIG" \
  --game shardy --module core --kind ui --rounds 5
```

原版Shardy的两个已知失败独立运行，保留正确断言；固定源码下预期得到业务 `failed` 和入口退出码1，不能算正常基线通过：

```bash
python -m gameqa run --config "$GAMEQA_CONFIG" \
  --game shardy --module known_defects --kind api --rounds 5
```

不加 `--module core` 的Shardy API选择会包含这两条失败。不指定任何过滤会选择全部游戏与已知失败，不能拿此结果冒充正常组。过滤来源是 `cases/` 中稳定ID的 `pytest.mark.case`，实际选择及每轮数量须以报告核对。

默认每次新建 `reports/<UTC时间>/`，每轮分别保存 `round-01`、`round-02`… 与 HTML、JSON 日志，UI另有截图；`summary.json`分别报告可重复性与全部通过。使用 `--report-dir` 时目标目录必须尚不存在。前置/清理失败是 `error`，业务断言失败是 `failed`，跳过或重试不能隐去；[现有真实证据入口](evidence/index.html)记录的是本次机器执行结果。

## 7. 受控缺陷与结束运行

受控Stendhal实验使用32161/8081、独立数据库和类路径，原版价格与测试预期保持不变。不要修改主服jar或将金币预期改为59；构建、多轮检出、数据恢复与停服记录见[注入缺陷报告](缺陷/注入-商店多扣金币.md)。其配置必须同时切换端口、Web URL及日志路径；缺陷服首次运行需要在32161独立开户。若实验涉及Android，另加 `adb -s emulator-5554 reverse tcp:8081 tcp:8081`，现有连接脚本只映射8080/3000/3001。

结束主服可在另一个终端执行 `sh scripts/stendhal/stop.sh main`；结束缺陷服用 `sh scripts/stendhal/stop.sh fault`，两者只停止各自PID。Shardy和客户端分别按本次保存的PID停止；模拟器用 `adb -s emulator-5554 emu kill`。数据库和AVD默认保留，重新运行沿用原账号密码，不自动清空数据。
