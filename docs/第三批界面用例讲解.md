# 第三批：装备放对位置，喝药真正回血

这一批把两个操作搬到Android模拟器中的真实游戏界面：把短剑装上、卸下并尝试放进错误槽位；连续喝两瓶药水，检查回血和最大血量限制。Airtest操作界面，独立管理员 `qaobserver`读取UI角色 `qaplayer`的服务器数据，再核验恢复。

**当前状态：本批两个UI执行ID均达到 `U`（已实现 UI 用例）；独立核查已完成。** [最终报告](evidence/stendhal-items-ui-final/index.html)、[多轮摘要](evidence/stendhal-items-ui-final/summary.json)、[独立核查](evidence/stendhal-items-ui-final/verification.json)和[启动前来源清单](evidence/stendhal-items-ui-final/source.json)已归档。正式组在原项目目录、原Python环境串行执行；123项执行源在首例运行前冻结且核对一致。本批没有重新从新目录或新Python环境执行，前三次校准失败继续保留。

两个ID×多轮，共10次通过，准备、执行和清理三阶段全部通过；无观察重试、无不稳定。独立核查确认5次装备往返、5次feet实际拒绝和10次真实Drink。10次恢复均逐字段核验通过，位置全部回到原格，没有相邻位置调整。

本组报告记录260次观察、230条断言、180次记录动作和245张截图。180次是报告记录层的动作计数，不等于180次游戏业务操作。结果来自上述独立核查，不能用截图数量推导功能覆盖率。

测试仍使用Stendhal 1.49，源码版本为 `cbe0825e9b46f2a8adf9adce8c5747ece13b17a0`。本批有两个执行ID：

| 执行ID | 关联设计 | 一次测试做什么 |
|---|---|---|
| `ST-BAG-UI-001` | 功能目录同名装备设计 | 卸下原木棍，短剑装上右手再卸回背包，然后尝试放进feet槽。 |
| `ST-BAG-UI-007` | 已有 `ST-BAG-API-007`药水设计 | 一份快照下连续喝两瓶药水：40/100→90/100→100/100；数量2→1→0。 |

药水界面用例是已有设计的界面验证，不新增一条设计；它只有一个执行ID，不因为喝了两次就计成两个子例。已有API药水的 `-heal`、`-cap`仍是各自独立准备和恢复的执行ID，两种组织方式要分别说明。

本批新增两个正常执行ID及10次正式多轮通过。第三批完成时全项目32个正常执行ID各有多轮证据，共160次通过；实现的34个执行ID还包含两条保持failed的已知原版缺陷。Stendhal设计目录仍是73条，21条接入自动化、52条尚未接入；本批只新增装备设计的接入，药水设计不重复增加。校准、框架自检和已有ID再次复跑均不重复相加。

## 短剑这条用例怎样检查

管理员先保存角色原来的状态，再准备一把short sword、XP800和安全地图起点。用例确认等级至少5、基础ATK为10，原右手确实只有club，左手、手指和脚部为空，背包最初只含第一格的一把短剑。这些是本地固定图片模板的前置条件；不符合时应停止，不能套用同一张图片判定。

移动道具使用原版手机操作：**长按道具→选择Hold→点击目标槽位**。Hold表示先拿住道具，再点它要去的位置。

| 步骤 | 真正的界面操作 | 独立检查 |
|---|---|---|
| 腾出右手 | 长按右手club，选择Hold，点背包空槽。 | club留在背包、右手为空；道具攻击系数 `atk_item=0`，界面显示 `ATK 10 x 0`。 |
| 装上短剑 | 长按背包short sword，选择Hold，点右手空槽。 | 短剑在右手、总量1，全部业务属性保持；基础ATK仍10，`atk_item=11`，界面显示 `ATK 10 x 11`。 |
| 卸下短剑 | 长按右手short sword，选择Hold，点背包空槽。 | 短剑回到背包、总量1，业务属性保持；合法往返的原版日志编号 `logid`保持。右手为空，界面恢复 `ATK 10 x 0`。 |
| 放进错误槽 | 长按背包short sword，选择Hold，点feet空槽。 | 聊天区域出现本次实际拒绝提示；短剑仍在背包，feet为空，背包及8个装备槽的完整数据含 `id`、`logid`均与尝试前一致，攻击属性保持。 |

错误槽测试必须同时看到“服务器拒绝了”和“物品没有丢失”。仅仅发现feet为空，不能排除操作根本没有送达。用例使用新的登录会话检查拒绝提示，避免把之前的旧聊天当成本次回复。

合法跨槽移动不能要求协议 `id`不变。实际运行的Marauroa 3.9.8在 `RPSlot.add`中调用 `assignSlotID`，而原版[DestinationObject](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/actions/equip/DestinationObject.java#L363-L368)把物品加入新槽时调用该方法。测试因此比较全部属性，仅在合法移动的业务属性比较中排除 `id`和 `logid`，同时确认短剑总量始终1；不是只比较物品名称。

第一次真实装备还可能建立原版审计 `logid`。用例先确认装备后的 `logid`非空，再确认卸回背包后仍相同，依据是[StendhalItemDAO](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/core/engine/db/StendhalItemDAO.java#L44-L65)及[ItemLogger](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/core/engine/ItemLogger.java)。非法槽拒绝没有发生跨槽移动，所以拒绝后的完整槽数据仍必须连同这两个编号一起保持。

## 药水这条用例怎样检查

管理员保存一次原状态，准备安全地图、最大HP100、当前HP40、minor potion两瓶，并确认没有主动战斗和持续状态，背包只含这堆药水。玩家使用**长按药水→选择Drink**，每次实际喝一瓶。

| 阶段 | 当前HP / 最大HP | 药水数量 | 为什么是这个结果 |
|---|---|---|---|
| 起点 | 40/100 | 2 | 固定测试数据；界面HP和背包数量也要匹配。 |
| 第一次Drink后 | 90/100 | 1 | 药水回复50HP，40＋50＝90。 |
| 第二次Drink后 | 100/100 | 0 | 90＋50超过上限，只能恢复到100；背包对应槽变空。 |

每次Drink后，管理员还比较最大HP、XP、金币和等级是否保持，检查没有新增持续状态或攻击目标。Airtest分别核对HP文字、药水数量标记和最终空槽。第二次喝药紧接第一次，仍在同一快照和同一执行ID内；用例结束只恢复最初保存的状态。

## 预期从哪里来

这些结果来自固定版游戏源码，不能根据跑出来的结果再改预期：

- [short sword配置](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/data/conf/items/swords.xml#L717-L735)规定攻击值11、最低等级5及合法装备槽。[道具攻击计算](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/RPEntity.java#L2755-L2775)与[统计栏显示](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/js/stendhal/ui/component/PlayerStatsComponent.ts#L140-L150)说明基础ATK与道具系数。`10 x 11`不是本例验证的每击伤害值。

## 怎样手动跑一条并定位

先在终端进入本地项目，并加载已有私有配置。`local.env`含本地配置与凭据，不要复制进报告或代码仓库：

```sh
cd "<repo>"
source ../../work/local.env
```

只跑装备这一条：

```sh
../../work/python-env/bin/python -m gameqa run --case ST-BAG-UI-001 --rounds 1
```

只跑药水这一条：

```sh
../../work/python-env/bin/python -m gameqa run --case ST-BAG-UI-007 --rounds 1
```

需要游戏服务和Android模拟器已经启动，两个UI用例按顺序运行。终端会给出本次报告路径。打开 `index.html`，按ID找到用例，再看失败的准备、执行或清理阶段；对应 `case.json`里的 `steps`和 `visual_observations`记录预期、实际、模板区域与截图，`metadata.reproduce`保留该次具体重跑入口。

[用例代码](../cases/test_stendhal_items_ui.py)写明操作顺序与预期；[StendhalUI](../src/gameqa/stendhal_ui.py)实现长按菜单及Hold移动；[AndroidDevice](../src/gameqa/device.py)执行Airtest触摸、定位和截图；[prepare夹具](../cases/conftest.py)与[独立管理员读取及恢复](../src/gameqa/stendhal.py)负责保存起点和核验恢复。手动定位应使用上述执行ID，不能把药水关联设计ID `ST-BAG-API-007`当作这条UI测试的运行入口。

## 恢复与覆盖边界

两条用例分别使用一份R1快照：保存运行前角色状态，管理员准备数据，玩家实际操作，最后恢复并比较支持的背包、装备、属性、任务、位置及计数等字段。恢复是独立检查；不能只看到 `restored=true`就跳过恢复前后字段核对，恢复失败也不能当正常通过。

本批验证背包与装备槽、界面属性、即时药水消耗和回血封顶。没有验证战斗界面、随机伤害或世界掉落，也没有验证交战时治疗与伤害事件的先后顺序。R1仍不回滚银行、成就数据库、持续状态、审计日志或整个世界；这些范围不能由本批通过推导。

本讲解保留第三批完成时的统计。第四批已补真实战斗界面，最新数量和证据见[验收清单](验收清单.md)与[第四批讲解](第四批战斗界面用例讲解.md)。
