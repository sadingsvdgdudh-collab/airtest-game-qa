## 一次测试里发生什么

UI玩家是 `qaplayer`，管理员是另一个账号 `qaobserver`。管理员不代替玩家接任务、交材料或领奖，只负责保存起点、准备数据、读取结果和恢复。

| 阶段 | 谁在操作 | 检查什么 |
|---|---|---|
| 保存并准备 | 管理员 | 先保存角色原来的状态，再准备100金币、beer1、XP0、karma20、尚未接送酒任务，放到守卫室 `int_semos_guard_house` 的固定起点 `(7,11)`，保持在Hayunn整条巡逻路线的对话范围内。确认0级时最大HP为100，这是本例固定图片模板的前置条件。`meet_hayunn=done`避免新手教学奖励混入本次任务。 |
| 接取 | UI玩家 | 在游戏聊天框依次输入 `bye`、`hi Hayunn Naratha`、`task`、`yes`。管理员检查送酒任务变为 `start`，金币仍100、XP仍0、karma仍20、beer仍1。 |
| 进行中日志 | UI玩家与Airtest | 输入 `/progressstatus`打开TravelLog，实际匹配任务标题和“承诺给Hayunn送酒”的正文，然后关闭窗口。 |
| 交付 | UI玩家 | 依次输入 `bye`、`hi Hayunn Naratha`、`yes`，真实交付已经带在身上的beer。管理员检查任务变为 `done`，beer变为0，金币120、XP50、karma30。 |
| 成长与完成日志 | UI玩家与管理员 | 管理员检查角色从0级升到1级、最大HP增加10、当前HP回到新上限。Airtest检查Completed Quests正文，以及统计栏的四项显示：XP50、Level1、下一级尚需50XP、HP110/110。 |
| 实际断开和重登 | UI玩家与管理员 | 关闭游戏浏览器进程，管理员必须实际观察到原服角色离线；再重新登录并选择角色，管理员确认角色在线。 |

只接取任务不会奖励金币或经验。真正交付后才得到20金币、50XP和10karma。任务“完成”也不能成为重复领奖的入口。这些是固定版游戏的规则，并非测试为了通过自行规定的数字。

## 为什么奖励会升级

[BeerForHayunn](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/maps/quests/BeerForHayunn.java#L55-L97)规定任务日志、消耗一瓶beer、奖励和不可重复完成。[等级表](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/common/Level.java#L38-L43)规定0XP为0级、50XP为1级、100XP为2级，因此本例领奖后下一级还差50XP。[升级处理](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/RPEntity.java#L1162-L1175)规定每升一级最大HP增加10，当前HP恢复到新上限。

本例先确认准备后 `base_hp=100`，确保固定界面模板适用。管理员对升级结果仍按游戏规则计算“准备后的最大HP＋10”，并确认当前HP等于新上限；Airtest随后检查本例界面实际显示 `110/110`。如果起点最大HP不是100，应在前置检查处失败，不能把所有角色的正确结果都规定成110。任务槽保留原始完整值，包括完成时间和次数等后缀；重登后不仅检查第一个状态仍为 `done`，还比较完整任务槽是否保持。

## 截图与真正的界面断言有什么区别

截图用于回看过程。界面断言还会在指定区域寻找真实截图裁出的模板，记录匹配位置、阈值和成功或失败。

- 任务正文只在 `(290, 290, 597, 555)` 区域检查，避免把聊天记录里的任务文字当作TravelLog正文。
- 成长显示只在 `(0, 325, 96, 470)` 统计栏区域检查，匹配阈值为0.9。
- `xp-next-50.png`同时包含 `Level 1` 和下方剩余经验的 `(50)`，避免误匹配ATK或DEF旁边另一个相同的 `(50)`。
- `quest-unrepeatable.png`只在全新登录后的聊天区域 `(100, 575, 565, 1220)` 查找，阈值为0.9。先看到NPC对已完成任务的回应，再检查奖励没有增加；单看角色数据不变，不能排除请求根本没有送达。
- 图片定位失败保留当时截图，观察最多重试一次。即使重试成功，本次运行仍标记不稳定；接取、交付等业务输入不会自动重发。

[模板清单](../assets/stendhal/quest-templates.json)记录每张模板的原始截图路径、裁剪框 `crop` 和SHA-256。[进行中原图](../assets/stendhal/calibration/quest-start.png)与[完成原图](../assets/stendhal/calibration/quest-completed.png)留在项目中，可回查模板来自哪里。模板是固定模拟器分辨率720×1280下的真实画面，不是人为画出来的预期界面。

## 重登和恢复分别证明什么

重登检查在“角色确实离开服务器，再重新连接”的过程之后，已经获得的任务和奖励是否保持。`presence_observations`应包含目标角色 `online=false`，然后 `online=true`；只关闭窗口、刷新页面或等待几秒不能代替这一证据。

本地部署没有HTTP页面 `/account/logout.html`。因此本例验证的是实际游戏会话断开与重新登录，不能写成已经验收网站账号退出按钮或该HTTP退出接口。服务器重启后的持久化也不由这条用例证明。

R1恢复则用于把测试角色送回运行前的状态，让下一条测试能从自己的起点开始。它恢复约定的背包、装备、任务、金币、经验、血量、属性和位置等角色数据，并核验比较；它不回滚银行、成就数据库、持续状态或整个游戏世界。报告中的 `restoration.restored=true`要与实际恢复字段核验一起阅读。

## 代码和报告怎样对应

[用例文件](../cases/test_stendhal_quest_ui.py)列出起点、真实操作及预期结果。[StendhalUI](../src/gameqa/stendhal_ui.py)负责登录、聊天、TravelLog、图片检查与重登；[AndroidDevice](../src/gameqa/device.py)负责Airtest定位、输入、点击和截图。[Stendhal](../src/gameqa/stendhal.py)负责独立管理员读取角色、等待状态和在线状态；[prepare夹具](../cases/conftest.py)保证用例的状态准备可分段（每段先还原上一段）并在结束时恢复;[QaProbe](../adapters/stendhal_bridge/QaProbe.java)提供原服只读在线查询、角色检查和约定范围的恢复。

读报告时优先看这些记录：

- `steps`：预期、实际、规则来源，或实际界面操作。
- `visual_observations`：模板、查找区域、阈值、匹配位置，以及失败后留存的截图。
- `state_observations`：接取和交付后真实读到的角色状态。
- `quest_ui_reward_checkpoint`：第一次领奖后的奖励字段、beer数量和完整任务槽，用于重登后及重复对话后比较。
- `presence_observations`：确实离线和重新在线的服务器证据。
- `preparation`、`restoration`：运行前的原状态、准备后起点、恢复前后及核验结果。

第一组多轮未达到验收要求，完整保留。最终组按同一版本重新执行了全部多轮，独立核查确认两个ID各多轮通过、无跳过或执行错误、无不稳定、任务用例每轮实际离线重登、全部执行恢复核验完整。这次验收基于完整新组的结果，没有只重跑失败的一轮，也没有用后面的通过覆盖最早的失败。

## 登录故障和游戏缺陷怎样区分

可以把测试想成“先进入游戏，再检查任务”。用户名没有成功填入、没有进入角色，是登录准备或自动化操作的问题；这时不能据此认定游戏的任务奖励发错了。重登时发生同类故障，也要根据失败步骤、截图和服务器在线记录定位，不能只看报告里的红色结果就登记为游戏业务缺陷。

本轮的原始失败报告及截图完整保存。例如 [第二次校准](evidence/stendhal-quest-ui-calibration-2/index.html)和[第三次校准](evidence/stendhal-quest-ui-calibration-3/index.html)已完成任务领奖阶段，随后在重新输入用户名时失败；这两次记录均保留 `diagnostics.restoration.restored=true`及恢复前后字段核验。它们能证明失败后恢复了测试角色，仍不能代替整条用例通过或连续多轮验收。

新代码在输入前，先用真实截图裁出的 `username-focused.png` 检查用户名框的黑色焦点边框，限定区域为 `(170, 255, 352, 285)`、阈值为0.9；输入后，再检查用户名文字确实出现。离线反例使用原始失败截图 [login-unfocused.png](../assets/stendhal/calibration/login-unfocused.png)，要求未聚焦画面不能通过；真实聚焦截图则应通过。这两步分别回答“输入会落进这个框吗”和“文字已经进去了没”。

每次登录URL还带有唯一的 `qa_session` 标记，启动命令使用 `am start -W`等待返回。这些属于启动与输入保护措施。先前输入失败的具体根因仍未确定，Chrome仍存在多个标签页，因此没有把它们写成已证明根因或已验证标签复用的修复。

[第四次校准](evidence/stendhal-quest-ui-calibration-4/index.html)完整单轮通过，`unstable=false`且恢复核验成功；该轮尚未加入最终焦点守卫和NPC回应模板。[第五次校准](evidence/stendhal-quest-ui-calibration-5/index.html)使用当时待验收版本，准备、执行和清理均通过，`unstable=false`、`diagnostics.restoration.restored=true`。单轮通过不能代替多轮验收。

第一组多轮随后暴露了重登焦点故障，因此第五次单轮通过不能作为稳定性验收。验收版本把用户名输入前的操作改为固定两次默认 `0.01` 时长的原生短点击：先激活表单，再聚焦输入框；密码框也使用默认短点击。焦点守卫和文字守卫仍按0.9阈值检查，用户名文字只输入一次。已确认原先 `duration=0.2` 在ADBTOUCH中执行的是同点200毫秒滑动，但尚未证实它就是失焦原因。

[第六次校准](evidence/stendhal-quest-ui-calibration-6/index.html)中，两次短点击、焦点检查和实际输入成功，任务接取及TravelLog检查也通过；交付阶段的 `hi` 没有得到NPC回复，任务仍为 `start`，整条用例失败，`unstable=false`、恢复核验成功。截图26显示Hayunn已经走远。这是新的失败证据，不能因为登录步骤成功，就把本次运行记为通过。

[Hayunn的巡逻路径](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/maps/semos/guardhouse/RetiredAdventurerNPC.java#L92-L99)依次为 `(4,9)→(6,9)→(6,14)→(6,9)→(11,9)`。[SpeakerNPC](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/npc/SpeakerNPC.java#L220-L222)默认对话范围为5，[距离判断](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/npc/SpeakerNPC.java#L263-L279)要求横向和纵向距离分别小于5。只站在NPC当时的位置附近，稍后他走开就可能听不到对话。

新的测试准备将角色固定放在守卫室 `(7,11)`：与整条巡逻路线的最大横向距离为4，最大纵向距离为3。NPC继续按原版路线活动，任务和领奖仍由UI玩家真实聊天触发。[第七次校准](evidence/stendhal-quest-ui-calibration-7/index.html)完整单轮通过，准备、执行、清理三阶段均通过，`unstable=false`且恢复核验成功。随后最终组完整多轮与独立核查均通过；第六次距离相关失败及此前登录失败继续保留，用于解释测试起点和界面操作为何调整。

## 本例的覆盖边界

beer由管理员预先准备，角色也由管理员放到守卫室固定起点 `(7,11)`。因此这条用例覆盖真实接取、交付、任务日志、奖励、成长、断开重登和防重复领奖；它没有验证走出守卫室、跨地图到酒馆、购买beer再走回来的全程界面操作。

本批先完成这个任务代表流程。背包操作、药水使用和战斗界面仍需各自实现并验收，不能因任务用例里经验增加，就把完整战斗流程计为已覆盖。
