# ST-SHOP-OVERCHARGE：购买 cheese 每笔多扣 1 金币

这是**受控注入缺陷**，用于证明框架能从真实服务器交易中检出业务错误，不是原版 Stendhal 已确认缺陷。执行日期：2026-10-03（Asia/Shanghai）。结果：同一原用例连续多轮均 **failed**；预期余额60，实际余额59；准备、观察和恢复成功，零重试、零不稳定。

## 环境和规则

- Stendhal 1.49，源码 commit `cbe0825e9b46f2a8adf9adce8c5747ece13b17a0`，Marauroa 3.9.8；macOS ARM64，JDK 21.0.6，服务端最大堆内存512MB。
- 独立 `runtime-fault/`、H2数据库、TCP `127.0.0.1:32161`、HTTP `127.0.0.1:8081`。原版主服32160/8080持续运行；本实验没有登录或修改主服角色。
- 独立缺陷服重新创建 `qaplayera` 和管理员 `qaobserver`。玩家发送真实对话action，管理员使用另一连接读状态、准备与恢复数据。
- [原版商店配置](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/data/conf/shops/sell_items.xml#L6-L16)规定 Margaret 的 cheese 每个20金币。因此100金币购买2个后应为 `100 - 2×20 = 60`。
- [原用例 ST-SHOP-API-001](../../cases/test_stendhal_api.py#L25)保留预期60，没有接受59、`xfail`、跳过或弱化规则。其他用例未在本缺陷组执行。

## 复现

1. 构建并启动独立缺陷服，配置使用32161/8081及缺陷服日志路径。
2. 玩家登录为 `qaplayera`；管理员准备背包100金币、0个cheese，并移至 Margaret 的真实相邻可通行格。
3. 玩家依次发送 `bye`、`hi Margaret`、`buy 2 cheese`、`yes`，每个对话等待实际服务器处理。
4. Margaret 报价40并确认交易成功。独立管理员实际读取背包：2个cheese、59金币。
5. 原金币断言比较实际59与预期60，记录失败；退出用例时恢复准备前快照并核验。

在工作区根目录执行，密码由本地私有 `work/local.env` 注入，不包含在报告或命令参数内：

```sh
work/python-env/bin/python outputs/airtest-game-qa/scripts/stendhal/build_fault.py
outputs/airtest-game-qa/scripts/stendhal/start.sh fault
```

保持服务运行，在另一终端执行。报告目录必须尚不存在，避免覆盖旧证据：

```sh
source work/local.env
work/python-env/bin/python -m gameqa run \
  --project outputs/airtest-game-qa \
  --config work/config.fault.toml \
  --case ST-SHOP-API-001 --rounds 5 \
  --experiment ST-SHOP-OVERCHARGE \
  --report-dir work/reproduced-stendhal-injected
```

预期执行器退出码为1，因为业务断言必须保持失败。缺陷服首次运行需通过桥在32161创建账号及角色；[开户原始记录](../evidence/stendhal-injected/bootstrap/qaobserver.json)保留了真实服务端结果并遮蔽密码。

## 定位与差异

缺陷位于 [SellerBehaviour.java](../../integrations/stendhal/defects/overcharge/SellerBehaviour.java#L110)的 `transactAgreedDeal`：110行限定 `cheese` 与完整匹配 `qaplayer[a-z]*` 的角色名；111行给本笔交易总价加1；117行用此总价真实扣款。它作用于购买cheese的所有商人，没有将触发条件写成仅 Margaret。裸名 `qaplayer` 也匹配，小写字母后缀可匹配，数字不匹配。成交检查使用加价后的金额，实际扣款仍须满足金币足够且成功放入背包。

原版与注入源码只相差新增的7行。[最小diff](../evidence/stendhal-injected/overcharge.diff)与两份源码的实际比对逐字节一致。`fault/classes/` 中该类排在原版jar之前，主服类路径不含该目录；[启动与停止记录](../evidence/stendhal-injected/lifecycle.json)保留了实际命令和监听状态。

## 恢复与回归边界

每轮 `restore` 返回 `restored:true`，服务端先恢复再按已声明字段投影核验，成功后移除快照。数据恢复后金币为准备前的0，cheese回到准备前数量；原地图 `int_semos_guard_house` 的 `(8,12)` 精确恢复，未使用相邻格放宽。`npc_purchases`、`npc_sales`、`looted_items` 与准备前快照一致；购买产生的 `bought.cheese:2` 被清除，八类 `item_counter_cache` 均恢复为空。比较基准是 `preparation.before` 与 `restoration.after`；`restoration.before` 是成交后的恢复起点。逐轮独立核验见[verification.json](../evidence/stendhal-injected/verification.json)。

恢复范围还包括完整背包/八个装备槽、任务、经验、HP、等级、基础HP、karma、攻防技能及其经验、`!kills`/`!tutorial`/`!visited`/`skills`。不宣称恢复银行、状态效果、成就、数据库审计日志或整个世界。

多轮结束后执行 `scripts/stendhal/stop.sh fault`，只停止缺陷服并保留H2数据库；主服持续运行。去除注入的方式是连接原版主服32160并使用原配置。原版主服相同用例已独立完成多轮回归，5/5 passed、零重试，每轮余额60、cheese2、restored:true，见[恢复回归报告](../evidence/stendhal-restored/index.html)与[摘要](../evidence/stendhal-restored/summary.json)。此前一次恢复组首轮被遗留UI会话占用NPC而失败，已保留[原始记录](../evidence/stendhal-restored-first/index.html)；补上UI结束对话和断开后重新完成本组多轮。本报告不把稳定检出注入失败算作原版业务通过。
