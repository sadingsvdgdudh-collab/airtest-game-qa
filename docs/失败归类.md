# 失败归类：业务 / 环境 / 框架

> 一句话：**同一个“红”，可能是游戏坏了，也可能是后端没起，也可能是自己用例写错。**
> 这三种混在一起看，等价于把环境噪音算成缺陷。所以每条执行都要带一个 `failure_class`。

## 三类是什么

| 类别 | 含义 | 长相 | 该谁处理 |
| --- | --- | --- | --- |
| `business` | 断言跑完但不成立 | `outcome=failed` + 断言的期望/实际 | 开发 / 策划 |
| `environment` | 基础设施打断 | `outcome=error` + 命中基础设施签名 | 测试环境（起后端、重连、换设备） |
| `harness` | 既不是业务也不是已知环境 | 用例/封装自己写错（TypeError、fixture 少参） | 你 |
| `skipped` | 缺能力没跑 | `outcome=skipped` | 补能力 |
| `none` | 通过 | `outcome=passed` | — |

## 判定规则（`gameqa.evidence.classify_failure`）

```
failed 且（有断言步骤 或 文本含 AssertionError）→ business
failed 且命中基础设施签名                    → environment
failed 其余                                  → harness
error  且命中基础设施签名                     → environment
error  其余                                  → harness
```

**为什么要看“有没有断言步骤”而不是只看文本**：断言消息里可能恰好引用了
`Game connection closed` 这类文本，按文本判会把业务失败误判成环境失败。
所以 `failed` 先看断言，再退到签名。

基础设施签名（`gameqa.bridge.INFRA_SIGNATURES`）：

```
is not online / Game connection closed / TimeoutException / SocketException /
EOFException / bridge exited / no confirmed response / handshake did not complete
```

## 落在哪

| 位置 | 字段 |
| --- | --- |
| `case.json` | `failure_class` |
| `summary.json` | `failure_counts{business,environment,harness,skipped}`、`business_failures[]`、`environment_failures[]`、`harness_failures[]` |
| 面板结果页 | 三列分开：**业务失败 / 环境失败 / 未分类**（老报告没分类字段，落进未分类，不静默丢） |
| Allure | 标签 `failure_class:<类>` |

## 和重试的关系

- `business` **永不重试**——重试就是掩盖缺陷。
- `environment` 会重试一次（`--retry-infra 1`），恢复后记成 **重试才过**，仍不计一次通过。
- `harness` 不重试——自己写错的，重试一百次还是错。

## 实测（2026-10-27）

| 场景 | outcome | class | 报告 |
| --- | --- | --- | --- |
| 后端正常，SH-DEFECT-API-002 八步清盘 | failed | **business** | `business_failures=[SH-DEFECT-API-002]` |
| 后端停掉，SH-DEFECT-API-001 握手超时 | error | **environment** | `environment_failures=[SH-DEFECT-API-001]` |

两条用例同一天、同一个报告目录结构，一眼能分出“游戏坏了”和“环境没起”。

## 判读口诀

> **看 `failure_class`，不看颜色。**
> `business` 找开发，`environment` 找环境，`harness` 找自己。
