# 功能测试设计

功能设计先于自动化。用例进入代码前，需要明确规则来源、可控制的初始状态、业务操作、可信结果、恢复方法。不能因“界面操作没有报错”判定业务通过。

## 首条链路：商店购买

目标：验证真实玩家购买一种可堆叠道具后，金币按单价扣除、背包数量按购买数增加；下一轮能恢复到同一起点。

1. Android游戏客户端先登录目标角色，确保目标在线；接口用例使用另一玩家账号。
2. 独立管理员读取并保存目标角色数据，准备足额金币、空余背包和商店位置，检查返回角色名。
3. Airtest 在界面完成 NPC 对话和购买确认；管理员辅助接口不执行购买。
4. 等待服务器处理完成，读取金币与道具数量。单价来源固定版本的 NPC 商店配置；规则冲突时标记待确认。
5. 对比预期/实际，保存相关截图、协议消息、服务器日志和初始/结果状态。
6. 恢复快照并核对恢复结果；轮数按目的自定（冒烟 1 轮，验稳定性多跑几轮）。

异常扩展：金币不足、恰好够付、数量为零/负数、背包容量不足、重复确认、购买后出售/使用的跨系统影响。尚未实施的设计用例不计为已执行。

## 判断与失败分类

- 业务断言失败：直接失败，不重跑业务动作。
- 连接/识别瞬时失败：观察最多重试一次，保留第一次证据；恢复成功仍标记不稳定。
- 发送动作后未收到响应：结果不确定，不能重发购买；先读状态，无法确认则报错。
- 前置环境/恢复失败：报错，不能算业务通过。
- 规则来源冲突：待确认，不能以当前实现自证预期。
- 原版缺陷与受控注入缺陷分别标识；缺陷实验不修改预期以制造通过。
