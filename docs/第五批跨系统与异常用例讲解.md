## 任务链：从没有酒到真正完成任务

管理员只在开始时保存角色并准备20金币、beer0、XP0、level0、karma20、`meet_hayunn=done`、未接送酒任务和守卫室位置`(7,11)`。这之后的接取、地图移动、买酒和交付都由真实Android界面完成，中途不辅助添加beer或把任务设置为done。

路线为：**守卫室→Semos村庄西部→Semos城→酒馆→Semos城→村庄西部→守卫室**。涉及四张地图、六次地图切换。当前实现通过Airtest实际点击原版小地图行走，只有村庄与城镇间的两次出界仍点击主画布边缘，让原版`Ground.extend`触发切图。只读服务器坐标用于确认每个路点确实到达。每一步有界面截图和位置证据，不能把最后一次位置正确当作整段走路已完成。

原版[MiniMapComponent.onClick](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/js/stendhal/ui/component/MiniMapComponent.ts#L214-L236)直接调用游戏客户端的`moveto`，避开主画布点击实体时默认执行的Look或Attack；出界仍走原版[Ground.onclick](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/js/stendhal/entity/Ground.ts#L61-L81)。全部动作来自真实触摸，不新增GM移动字段、不从测试接口直接发送移动RPC、不改NPC或rat的AI。

小地图坐标来自两批共20个真实触摸点（8＋12）的被动DOM监听。监听只记录原生MouseEvent，不提交游戏动作；全部20点匹配实际公式：`offsetX=round((屏幕x−0.5)×980/720)`、`offsetY=round((屏幕y−202.55)×980/720)`。这里的origin x=0.5、y=202.55来自Chrome子像素布局的测量拟合，包含布局与边框的实际影响，不再用“简单扣1个CSS边框像素”猜测。真实屏幕点击`(53,268)`对应`offset=(71,89)`，屏幕x=37实际offsetX=50；旧估计49会把64格地图的目标24误选为25。

全部20点已冻结在[投影自检](../tests/test_stendhal_route_projection.py)第三项测试中，并遍历三种地图尺寸的全部格子，校验原版向下取整后仍选中目标格。该文件3项自检通过；全框架共41项，均与真实业务通过数分开。当前限Android720×1280和CSS缩放720/980，小地图128像素缩至约94物理像素后的舍入必须按实测处理。

正式路线共44次点击：42次小地图、2次出界主画布。村庄横穿y46；`(32,46)→(41,46)`之间由原版寻路绕开`(35,46)`树，静态确认最短可走路段为11格。城镇西段走y47避开Carmen在y46的巡逻，到x19转y46避开东段y47墙及NPC，再经`(42,39)→(42,37)`入酒馆；返程逆向，出界用y46。此前y43/44及y45路线失败位置保留。原版NPC巡逻是真实风险，但不能把尚未排除的投影误差直接判断成NPC占格。该固定路线已完成校准并正式多轮通过，不因为静态地块可走就宣称动态占格一定通过。

## 没有存储位置：拒绝购买也必须真的发生

只把背包塞满会漏掉一个原版行为：cheese还可以放在左右手，某些物品的内部容器也能接收它。因此本例同时占满背包和双手，排除背包扩容、嵌套容器与活动贸易，并确认所有槽都没有可合并cheese堆。

构造仍走真实业务：准备100金币、buckler和10种普通武器形成12槽；玩家把buckler装备到左手，右手原club保持，背包腾出一槽；真实购买一个apple花10金币填回最后一槽。此时**金币90、背包12槽、双手均占用**，才开始测试cheese购买。

实际`buy cheese`得到20金币报价，报价不改数据；再只确认一次`yes`。原版应回答`cannot equip the piece of cheese.`，金币仍90，所有角色槽没有cheese，完整槽数据包括协议ID和审计logid、交易金额及全部物品计数缓存都保持。管理员还读取目标角色所在区的地面cheese实体，比较前后没有新增或转移，不能用管理员另一张地图的客户端视野代替。

[SellerBehaviour](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/npc/behaviour/impl/SellerBehaviour.java#L101-L125)先调用`equipToInventoryOnly`，成功才扣款并更新交易记录；失败直接拒绝。[RPEntity的存储搜索](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/RPEntity.java#L1961-L2103)说明合并、空槽递归和另一条独立的地面回退路径。本例的商店失败不会调用任务发奖使用的地面回退。

[无空间代码](../cases/test_stendhal_shop_no_space.py)只覆盖这条拒绝子例。目录006的“满槽但可合并时购买成功”仍待执行，不把一个子例通过写成整个容量设计全部通过。

## 远距离攻击：选中目标不等于伤害生效

原版允许近战角色选中远方rat，所以本例不会错误要求攻击目标始终为空。玩家带原club选择一次远方rat；管理员逐次读取原版邻接关系、实际距离、角色武器射程、目标和原服回合。

本例按club原版攻击rate=4，观察至少两个实际攻击周期，即至少8个原服回合。整个窗口须非邻接、距离超过射程、目标仍是本夹具rat；rat始终20HP、没有尸体，也没有本玩家的命中、未命中或伤害事件。角色HP、XP、金币与击杀记录保持。若rat走近，或窗口不够长，不能凭最后HP没变判通过。

依据是[近战距离判定](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/core/rp/StendhalRPAction.java#L302-L317)和[club攻击频率](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/data/conf/items/clubs.xml#L28-L38)。rat保留原版AI；夹具只改变安全放置位置，不辅助冻结、削血或决定战斗结果。

## 取消攻击：先证明在打，再证明停止

玩家等原rat自然靠近后，只发一次Attack。测试必须先收到属于本玩家的正伤害事件，独立读取rat生命确实从20下降且仍存活，才发送一次原版`stop`，带空字符串`attack`字段。

之后同时从原服和实际客户端确认攻击目标清空；以停止确认时的rat生命为新检查点，再观察至少两个实际攻击周期。窗口中目标保持空、rat存活、HP保持、没有尸体，也没有本玩家继续攻击的命中、未命中或伤害事件。角色仍存活，XP、金币和击杀记录不增加。

停止玩家攻击不代表rat停止自主反击，因此不要求玩家HP保持原值，也不辅助让rat一起停止。这一区分能避免测试因为怪物正常反击而误报。

[StopAction](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/actions/attack/StopAction.java#L34-L41)处理原版停止请求，[RPEntity.stopAttack](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/RPEntity.java#L1240-L1255)清理攻击目标。两条异常都在[战斗异常代码](../cases/test_stendhal_combat_edges.py)中，rat与对应尸体按专用fixture身份清理，随后才恢复角色。

## 故障演练：失败只重读，不重复买

这是明确标记的受控定位失败，不伪装成上游游戏缺陷，也不计新增正常用例。它复用原`ST-SHOP-UI-001`业务，在真实界面用100金币买2个cheese，先独立确认金币60、cheese2。

随后主动把“已完成任务日志”模板放到当前地图区域查找。第一次应定位失败并保存截图与失败尝试；恢复时只改为正确的Send按钮模板，再读取屏幕。整个观察闭包没有对话、触摸或购买。重试成功后仍保留`unstable=true`，报告中的首次失败不会被覆盖。

演练检查观察前后金币均60、cheese均2，真实购买确认`yes`只提交一次。保存数据、恢复角色并关闭界面后，用新的独立进程、新快照、原版定位逻辑复跑`ST-SHOP-UI-001`一轮；复跑必须正常通过且没有观察重试或不稳定，才能完成本次演练核验。

[演练脚本](../scripts/exercise_observation_failure.py)、[保留首次失败的受控报告](evidence/stendhal-observation-fault/controlled/index.html)、[恢复后的独立复跑](evidence/stendhal-observation-fault/recovered/index.html)和[演练核验](evidence/stendhal-observation-fault/verification.json)均单独定位。**演练核验完成，首败及unstable保留，独立复跑稳定通过**；不能把受控报告的`passed + unstable`算成普通稳定通过。

## 怎样手动运行和定位报告

先进入本地项目，加载已有私有配置。不要把`local.env`中的凭据写进报告或仓库。

```sh
cd "<repo>"
source ../../work/local.env
```

四条执行ID各可精确跑一轮，按顺序运行，不共享账号或设备并行执行：

```sh
../../work/python-env/bin/python -m gameqa run --case ST-QUEST-UI-007 --rounds 1
../../work/python-env/bin/python -m gameqa run --case ST-SHOP-API-006-no-space --rounds 1
../../work/python-env/bin/python -m gameqa run --case ST-COMBAT-API-004-distance --rounds 1
../../work/python-env/bin/python -m gameqa run --case ST-COMBAT-API-004-cancel --rounds 1
```

游戏服务须已启动；任务链和故障演练还需要Android模拟器。要跑多轮，把对应命令的`--rounds 1`改为`--rounds 5`。终端返回本次报告路径，打开`index.html`按执行ID定位；`case.json`中的`steps`显示预期、实际和来源，`phases`区分准备、业务和清理阶段，`metadata.reproduce`保留精确重跑命令。

任务链重点看`quest_chain_checkpoints`和每段行走观察；无空间看`no_space_checkpoint`与实际NPC对话；战斗看远距/取消前后观察和按来源过滤的原版事件。只看界面没有动画或一次最终状态，不足以判断失败原因。

单独运行故障演练：

```sh
../../work/python-env/bin/python scripts/exercise_observation_failure.py --report-dir reports/manual-observation-failure-01
```

该目录必须不存在；再次演练请换一个新目录名，避免覆盖前次记录。脚本会先执行受控失败与恢复，再独立复跑原购买用例。
