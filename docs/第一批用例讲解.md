# 第一批：把正常流程扩展到异常和边界

这批新增8个设计条目，拆成14个可单独重跑的执行子例。重点是检查“玩家取消、输入特殊数量、拒绝任务、材料不足、刚好升级、接近满血”时游戏是否仍按规则处理。所有购买、接取、交付、使用动作由真实玩家协议发送；管理员只准备、观察和恢复角色。

主游戏固定为 Stendhal 1.49 / `cbe0825e9b46f2a8adf9adce8c5747ece13b17a0`。本批使用接口，不包含新增 Airtest 界面流程。任务接取的 TravelLog 界面显示还需单独验证。

## 每条用例怎样跑

1. 登录测试玩家和独立管理员，确认观察的是 `qaplayera`。
2. 保存角色原来的背包、任务、金币、经验、血量等，再准备需要的起点。
3. 玩家实际操作NPC或道具，每条业务消息只发送一次。
4. 等游戏处理，检查实际NPC回复和独立读取的角色状态。只看到“请求已发送”不能算通过。
5. 恢复快照并逐项比较。不通过、报错、重试或恢复失败都保留在报告里。

管理员快照不恢复成就数据库、银行、持续状态或整个世界。药水子例因此要求原角色没有持续状态、主动战斗，且最大HP大于60。该前置不满足时记准备错误。

## 为什么这些预期成立

cheese单价20来自固定版[商店配置](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/data/conf/shops/sell_items.xml#L6-L16)。[SellerAdder](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/npc/behaviour/adder/SellerAdder.java#L129-L209)规定数量上限、报价、yes成交和no取消；[Expression](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/common/parser/Expression.java#L85-L97)把小数数量按Math.round取整。1.5不是本版服务器拒绝的输入。

送酒只收1瓶，奖励20金币、50XP和10karma；拒绝接取扣5karma，来自[BeerForHayunn](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/maps/quests/BeerForHayunn.java#L77-L97)。经验50对应1级，100对应2级，来自[等级表](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/common/Level.java#L38-L43)；[升级处理](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/RPEntity.java#L1162-L1175)增加最大HP并回满血。

minor potion的[配置](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/data/conf/items/drinks.xml#L517-L538)为50；[Stuffer](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/item/consumption/Stuffer.java#L18-L25)一次拆出1瓶并立即治疗，[heal](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/RPEntity.java#L397-L420)限制回复不超过最大HP。它和食物的持续回血不同。

## 首轮失败怎样处理

首次14子例校准为11 passed、3 failed，保留[原始报告](evidence/stendhal-batch1-first/index.html)。另外的[诊断报告](evidence/stendhal-batch1-diagnosis/index.html)为2 passed、1 failed。三类原因各自处理：

- 零数量文案：测试写成“cheeses”，原版[PrefixManager](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/common/grammar/PrefixManager.java#L64)规定“pieces of cheese”。纠正文案匹配，零数量拒绝的业务预期不变。
- 购买确认：0.6秒时收到了玩家yes，还未收到下一回合NPC回复。原报告恢复前已经是金币60、cheese2，交易实际成功。现在轮询收到的消息，最长1.8秒；始终只发送一次yes。新增两项框架自检，验证晚到的回复和没有回复时都不会重发业务动作。
- 缺材料会话：直接准备任务start、beer0后重新问候，NPC无法进入会话。固定版[默认问候](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/maps/semos/guardhouse/RetiredAdventurerNPC.java#L76-L83)排除正在进行的送酒任务；[交付问候](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/npc/quest/SimpleQuestCompleteBuilder.java#L89-L93)又要求已有材料。[提醒分支](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/npc/quest/QuestOfferBuilder.java#L200-L211)只能在ATTENDING状态触发。修订003为真实接取后保持会话再请求交付，继续要求提醒、任务不完成、无奖励。返回NPC却没带材料的路径未由此例验收，其两次失败保持原样，暂不计为已确认游戏缺陷。

设计还有一处前置修订：原来的“H≥60，HP=H−60”在H=60时会得到HP0；原版不治疗已死亡角色，因此改为H>60。当前药水测试先核对这一条件。

## 自己重跑和读报告

先启动原版本地Stendhal主服，再在项目目录加载私有配置。此机器可按下面方式单独跑一条：

```sh
cd /Users/Zhuanz/Documents/Codex/2026-10-02/shi/outputs/airtest-game-qa
source ../../work/local.env
../../work/python-env/bin/python -m gameqa run --case ST-SHOP-API-005-fraction --rounds 1
```

要跑两个药水子例，可用 `--game stendhal --module inventory --kind api`，这也会选中已有背包堆叠用例。`--case`精确匹配执行ID；不能用父设计编号 `ST-SHOP-API-005` 代替五个子例ID。

打开报告后，先看用例ID和失败步骤，再看预期/实际和规则来源。`npc_dialogue`是NPC原文；`player_interface_messages`是玩家实际消息；`preparation`是起点和快照；`restoration`是恢复前后及核验；`server.log`是该用例期间的服务器日志。每例的 `metadata.reproduce` 给出同一ID的重跑命令。

如果购买返回不确定，先读取状态，不要立即再买一次。前置失败或恢复失败按error处理，不能当游戏规则失败或通过。接口用例没有UI截图，本批也不据此证明任务日志、背包图标或战斗画面的显示正确。
