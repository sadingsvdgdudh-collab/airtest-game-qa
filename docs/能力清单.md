# 框架能力与边界清单

用途：给「需求 → 用例」和「用例 → 可自动化代码」提供一份**框架真实能力**的输入，避免生成出来的用例按"AI 记得的框架"写，而不是按框架的真实边界写。

维护方式——**能由代码决定的段落一律自动生成**，人工只写代码读不出来的部分：

- 生成段（下面带 `generated` 标记的那段）：`python scripts/capabilities.py` 重写
- 过期自检：`python scripts/capabilities.py --check`（不一致返回 1）
- 人工段：通道矩阵、语义约束、恢复边界、验收口径、已知脆弱点

以下能力描述对应 `requirements-lock.txt` 固定的 airtest 1.4.3 / pytest 9.1.1 与 Stendhal 1.49 基线。

## 一、通道矩阵：断言落在哪里，就走哪条路

| 断言落在哪 | 本框架的通道 | 典型原语 | 对应 `自动化建议` |
|---|---|---|---|
| 服务端状态 / 协议参数 | 玩家协议桥（`Stendhal` / `Shardy`）+ 独立管理员观察（QaProbe） | `inspect`、`await_state`、`await_presence`、`dialogue` | `仅api自动化可用` |
| 界面可见结果 | Airtest + 模拟器内 Chrome | `StendhalUI.walk` / `say`、`AndroidDevice.touch` / `locate_image` | `UI自动化可用` |
| 两边都能发起并观察 | 双通道 | 上面两者组合 | `双通道均可用` |
| 原语齐，缺该场景的校准截图 | UI + 新资产 | `locate_image` + `assets/stendhal/*.png` | `UI自动化可做，需采集新资产` |
| 缺动作 / 准备 / 观测能力 | — | — | `当前框架能力不足`（明细写 理由/缺失能力/补齐办法） |
| 依赖人工主观判断 | — | — | `不建议自动化` |
| 尚未核对过能力 | — | — | `待核对框架能力` |

## 二、语义约束（写错就会产生假证据）

- **观察可以重试，业务动作绝不重发**：`Evidence.observe` 默认重试 1 次、上限 3 次，重试后即使恢复仍标 `unstable=True`；`Evidence.action` 一次都不重试。
- 发送后超时属于**结果不确定**（`IndeterminateAction`）：必须先读状态，禁止直接重发。
- **每个断言必须带规则来源**：`Evidence.check(title, actual, expected, source)`，`source` 为空直接抛错。
- **业务断言必须由独立管理员读真实状态**，不能拿界面文字当业务结论——界面显示 60 金币不等于服务端是 60 金币。
- **每个独立参数子例要重新准备快照、重建 NPC 会话**（新会话首句统一 `bye → hi <NPC名>`），不能共用前置。
- 业务失败记 `failed`，前置或清理失败记 `error`，跳过记 `skipped`；后两类不能计入验收。
- **API 与 UI 不能并发**：共用管理员会话、商店 NPC 和浏览器。UI 用例之间同样只能串行。

## 三、恢复边界（R1/R2/R3）

- **R1**（QaProbe 快照）：覆盖背包/装备、任务、XP/HP/level/base_hp、karma、位置、NPC 交易金额、`looted_items` 及物品计数缓存、atk/def 及其 XP、kills/tutorial/visited/skills；恢复后核验投影。
- **R1 不覆盖**：成就数据库、银行及其他容器、宠物、持续状态、世界实体、NPC attending、浏览器玩家会话。**涉及这些状态的用例不能声称"已恢复"。**
- 原位置被占用时，只允许报告并核验同地图曼哈顿距离 ≤1 的相邻格。
- **R2**：独立本地环境备份 `database/` 与持久世界状态，每条用例后停服恢复备份、重启并重登核对。涉及动态岛/尸体/采集节点/银行/多角色/房产/成就时必须用 R2。该环境重置尚待自动化。
- **R3**：保存并恢复 Android Chrome 设置/外观，结束后重启核对。

## 四、验收口径

- **轮数由使用者按目的自定**（冒烟 1 轮、改动验证按需、发布前多跑几轮），**不存在"必须跑固定轮数才算验收"**。面板上自定义勾选跑出来的运行标 `experiment=custom`，与固定分组的运行在报告里一视同仁地如实呈现。
- `consistent`（各轮结果一致）与 `all_passed`（全部通过）始终分开统计：多轮稳定失败是 `consistent=true` 但 `all_passed=false`，**不算通过**——这条口径与跑几轮无关。
- `unstable`（观察重试后才通过）不能计入干净通过；`skipped`、漏轮同样不能。
- 失败即停（`--stop-after-failure`）会缩短实际轮数，使 `consistent=false`——这是有意的，防止"跑了一半看起来通过"。
- 原版缺陷保留 `failed`，不使用 `xfail` 改成通过。

## 五、已知脆弱点（踩过的坑；生成用例时要避开或显式标注）

| 脆弱点 | 现象 | 规避 |
|---|---|---|
| 行走目标格被 NPC/怪物占用 | 原版 `moveto` 无法站上被占格，角色原地不动 → 等待超时判失败（实测 `ST-QUEST-UI-007`：目标格正南是 NPC Gordon，35 秒内 58 次采样位置与 speed 均不变） | 目标格避开 NPC 常驻点；或把到达判据放宽为"同地图且与目标格切比雪夫距离 ≤1 且 speed==0" |
| 模拟器重启丢 `adb reverse` | UI 用例连不上 8080（本机实测两次） | 重启后必须重跑 `scripts/android/connect.sh`；面板已加自动重连 |
| 固定 720×1280 / 320dpi + 模板阈值 0.9 | 换分辨率、机型、语言或游戏版本就要重新校准全部模板 | 换环境后重校准，并在资产清单里登记来源截图 |
| 端口探测不能用 `lsof` | 权限受限环境会报 `status error` | 用纯 Python socket 探测 |
| **快照卡住（上次运行被杀）** | 一次没走到 restore 的运行会把快照留在**主服内存**里，之后该角色的每次 `prepare` 都被拒。现在两条路自愈：① `Stendhal.prepare` 遇到这个错误会先`forget(older_than_seconds=60)` 再重试一次（只丢陈旧的，避免误删并发会话的快照），自愈记录写进 `diagnostics.snapshot_self_heal`；② 人工工具 `cleanup_characters.py` 会先丢弃该角色全部快照再清状态。 | 先看 `snapshot_self_heal`：`forgotten` 非空=已自愈；为空说明快照很新（可能真有并发会话）→ 再点「清理角色状态」或重启主服 |
| **买过之后换 NPC，第一次确认会被吞** | 真实买过之后，第一次向另一个 NPC 确认（`yes`）会被忽略：报价正常返回，`yes` 没有任何回应、钱货不动；单段（没买过）或重开一次会话（`bye` → `hi` → 再卖）都正常。实测 `ST-SHOP-API-009`：直接卖被吞，重开会话后 60→65 成交。 | 跨 NPC 交易用例在第一次确认被吞时**重开一次会话再确认**（本用例就这么做），并把该现象留档；不要用"改断言"绕过 |
| NPC 会话未释放 | 下一条用例撞 `NPC busy` | 用例结束真实 `bye` 并释放会话 |
| 同一 AVD 起第二个实例 | `FATAL Running multiple emulators with the same AVD` | 启动前先 `adb devices` |
| 报告目录按 UTC 时间戳命名 | 按本地时间找不到今天的报告 | 用 `ls -lt reports/` 或面板「结果」页 |
