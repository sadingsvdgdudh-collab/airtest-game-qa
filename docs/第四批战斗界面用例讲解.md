# 第四批：在界面攻击rat，检查击杀、经验和恢复

这一条把已有接口击杀流程搬到Android中的真实游戏界面：先卸下木棍、装备短剑，再长按rat并选择一次Attack。之后只读取服务器状态，等原版战斗结束。Airtest负责玩家操作，独立管理员负责准备、观察和恢复；管理员不代做攻击或发放击杀经验。

**当前状态：修正后正式多轮5/5通过，所有准备、业务和清理阶段均通过，无不稳定或观察重试；5次怪物/尸体清理和角色逐字段精确恢复通过。** [正式报告](evidence/stendhal-combat-ui-final/index.html)、[核验](evidence/stendhal-combat-ui-final/verification.json)和[独立审查](evidence/stendhal-combat-ui-independent-review.json)已归档。首次未通过组和校准单独保留，不加入正式通过次数。

| 执行ID | 关联设计 | 数量怎样算 |
|---|---|---|
| `ST-COMBAT-UI-001` | 功能目录已有`ST-COMBAT-API-001`击杀与装备设计 | 新增一个UI执行ID，设计不重复增加；目录仍73条、21条接入、52条待接入。 |

规则版本仍为Stendhal 1.49，源码commit `cbe0825e9b46f2a8adf9adce8c5747ece13b17a0`。本例使用同一Android14、720×1280模拟器和专用UI角色`qaplayer`。

## 一次测试实际做什么

管理员先保存角色原状态，准备XP800、HP100、一把short sword和守卫室`int_semos_guard_house (12,5)`。用例确认原右手只有club、背包只有短剑、等级至少5，且没有持续状态或主动攻击。HP100是当前生命，最大HP按准备后的角色状态核对，不能把它误当成100。战斗夹具还限制原rat累计击杀数低于9，避免本次触发不在R1恢复范围内的成就。

| 顺序 | 玩家操作或观察 | 检查什么 |
|---|---|---|
| 1 卸木棍 | 长按右手club，选择Hold，点背包空槽。 | 右手为空，club仍有1件。Hold表示先拿住道具，再放到目标槽。 |
| 2 装短剑 | 长按背包short sword，选择Hold，点右手空槽。 | 右手短剑1件、全身短剑总量1；界面右手显示短剑，统计栏显示XP800。 |
| 3 准备目标 | 管理员放置一只原版rat副本，保存专用`fixture_id`。 | rat的HP20、ATK8、DEF3、内部XP100；保留原版AI和属性，只增加对应尸体引用以便精确清理。只读等待最多10秒，连续两次同一相邻位置、speed0，再等0.6秒界面插值。 |
| 4 打开菜单 | 在地图区域找到rat文字标签，取其中心点向下30像素，长按身体0.5秒。 | 真实Action菜单出现，匹配其中的Attack；不使用管理员地图坐标代替屏幕定位。 |
| 5 攻击一次 | Airtest点击这一次菜单中的Attack。 | 走原版客户端攻击请求；此后不因等待或失败再点击Attack。 |
| 6 等待死亡 | 最多45秒，每约0.3秒只读一次该夹具状态。 | rat离开地图后停止等待；到期仍存在就按断言失败，不能辅助杀死它。 |
| 7 检查结果 | 管理员读角色和目标，Airtest核对界面。 | 击杀、尸体归属、经验、存活和界面显示相互对应。 |

一次Attack会启动原版连续战斗，不代表玩家只挥一剑。等待时读取多次状态属于正常轮询，不是重复发送业务，也不是把失败重跑成成功。45秒是本例等待上限，不是断言每次击杀都耗时45秒。

## 为什么这些结果可信

| 判据 | 预期 | 为什么不能只看一张截图 |
|---|---|---|
| 目标死亡 | 指定rat不在地图，保留的rat对象HP为0。 | 画面暂时找不到rat，也可能是它移动了。 |
| 对应尸体 | 同一rat的尸体存在，`killer=qaplayer`。 | 要排除其他尸体或其他玩家击杀。 |
| 经验 | 服务器XP800→805，界面分别显示800、805。 | 成功消息和升级动画不能代替实际数值。 |
| 单人击杀 | `solo.rat`相对战前增加1。 | 与尸体归属共同核对本角色独立击杀。 |
| 玩家存活 | `0 < HP ≤ 100`。 | 战斗伤害随机，不把素材中的HP64等值当固定预期。 |
| 其他状态 | 等级和最大HP不变；金币、club数量及右手短剑数量保持。 | 本例不操作尸体槽，不应把掉落自动算进背包。 |

XP加5有完整固定来源：[rat配置](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/data/conf/creatures/rodent.xml#L36-L59)中的experience是5，[加载器](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/core/config/CreaturesXMLLoader.java#L206)乘20得到内部XP100，[rewardKillers](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/entity/RPEntity.java#L1567-L1628)再乘0.05并按伤害贡献分配。单人完成全部伤害，因此获得5XP，并记录单人击杀。

[原版ActionContextMenu](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/js/stendhal/ui/dialog/ActionContextMenu.ts#L67-L86)发送目标实体的原版请求，[AttackAction](https://github.com/arianne/stendhal/blob/cbe0825e9b46f2a8adf9adce8c5747ece13b17a0/src/games/stendhal/server/actions/attack/AttackAction.java)启动攻击。辅助夹具[QaCombat](../adapters/stendhal_bridge/QaCombat.java)只布置目标、读取状态和精确清理，尸体由原版`makeCorpse`生成。

## 模板来自哪些真实画面

[战斗模板清单](../assets/stendhal/combat-templates.json)记录5张模板的原图、裁剪框和SHA-256；本次已只读核对，模板字节与原图对应裁剪一致，哈希一致。素材为[rat与XP800](../assets/stendhal/calibration/combat-rat.png)、[Attack菜单](../assets/stendhal/calibration/combat-menu.png)、[另一个菜单位置](../assets/stendhal/calibration/combat-menu-position-2.png)和[击杀后XP805及尸体](../assets/stendhal/calibration/combat-killed.png)。

| 模板 | 查找区域 | 阈值 |
|---|---|---|
| rat-title、rat-corpse | 地图`(96,203,565,555)` | 0.9 |
| attack-menu | 同一地图区域 | 0.85 |
| xp-800、xp-805 | 统计栏`(0,325,96,470)` | 0.98 |

标签中心向下30像素和长按0.5秒是这套固定分辨率下的真实操作校准值。rat会移动，代码先等其自然靠近并停稳，再找当前标签；不会把素材中的绝对坐标写成固定攻击位置。

Attack菜单在第二个真实位置的置信度是`0.89335477`，低于旧阈值0.9。当前只把Attack匹配阈值设为0.85，同时保留第二位置和反例检查：[离线检查代码](../tests/test_stendhal_combat_ui_observations.py)要求能认出两处Attack，不能把同菜单的Look、Push行或无菜单画面当Attack；XP800/805也不能互相认错，活rat画面不能当尸体。离线图片检查与真实游戏执行分别统计，不能由检查代码存在推导正式多轮通过。

原图中的Corpse窗口和掉落物品是模板来源画面的一部分。本UI用例只匹配地图尸体及XP，不点击尸体槽，也不据此宣称拾取或随机掉落内容已验证。

## 清理为何必须按顺序

本例结束时按**确认在线→必要时重登→清理rat/尸体→R1恢复角色→关闭UI**执行，失败也走清理阶段。

1. 独立管理员先查询UI角色是否在线，并核对角色名。若已离线，由UI正常重新登录，再等服务器确认在线；管理员辅助只能操作在线的目标角色。
2. 根据本例`fixture_id`清理持有的rat及其对应尸体，停止相关攻击与路径，确认`rat_present=false`、`corpse_present=false`。不扫描并删除其他玩家或地图实体。
3. 恢复最初R1角色快照，保存恢复结果。正式验收还要逐字段核对支持的恢复投影，不能只摘录`restored:true`。
4. 最后UI发送bye并关闭Chrome连接，避免在角色恢复前就断开，留下无法清理的目标。

顺序由[rat_fixture](../cases/test_stendhal_combat.py)、[prepare及UI夹具](../cases/conftest.py)与[StendhalUI.close](../src/gameqa/stendhal_ui.py)共同实现。离线自检覆盖在线、离线两条路径；另一次[真实断线演练](evidence/stendhal-combat-ui-disconnect-recovery/index.html)实际退出后由共享清理夹具正常UI重登、清理并恢复。正式多轮清理前均在线，没有触发额外重登。该演练不算新增正常用例。

R1只恢复约定的角色背包、装备、属性、任务、位置和计数等字段；rat及尸体由专用夹具另清理。血迹、审计数据库日志、银行、成就和其他世界状态不在这次回滚范围内。本例没有验证固定每击伤害、固定击杀时长、技能成长、掉落拾取、战中治疗、死亡复活或独立挑战。

## 怎样在本机手动跑一次

先确保本地原版游戏服务和同一Android模拟器已启动，进入项目并加载已有私有配置。`local.env`含本地配置与凭据，留在私有工作目录。

```sh
cd "<repo>"
source ../../work/local.env
../../work/python-env/bin/python -m gameqa run --case ST-COMBAT-UI-001 --rounds 1 --experiment manual-combat-ui
```

运行器会完成登录、准备、真实界面操作、观察和清理，不要同时运行其他共享模拟器/角色的用例。终端输出新的报告目录；打开其中`index.html`，按`ST-COMBAT-UI-001`查看步骤、规则、预期/实际和截图。再看`case.json`的`phases`、`visual_observations`、`combat_observations`、`combat_cleanup_presence`及`restoration`，区分准备、业务或恢复失败。`metadata.reproduce`保留该次重跑入口。

实现入口是[战斗UI用例](../cases/test_stendhal_combat_ui.py)。手动跑UI用上述ID，不使用关联设计的`ST-COMBAT-API-001`，也不在等待期间补点Attack。
