# 用例编写协议（人 / AI 通用）

用途：从设计条目生成**用例体**时按这份协议做。它由 2026-10-08 的 AI 生成试点 A 组验证过（2 条用例，一条一次通过、一条改 1 处后通过），并吸收了当时实测到的三个坑。

## 一、只能使用这些输入

| 输入 | 位置 |
|---|---|
| 设计条目（前置 / 动作 / 预期与判据 / 来源 / 恢复） | `docs/功能用例目录.md` |
| 可用原语（自动生成） | `docs/能力清单.md` 的「A. 原语」 |
| 规则出处常量 | `src/gameqa/sources.py` |
| 业务域词汇（NPC 名与有意图的动作） | `src/gameqa/shop.py`、`src/gameqa/quest.py` |
| 现成模板 | `cases/` 里已迁移的用例（shop / quest 两个域） |
| 门禁规则 | `src/gameqa/hygiene.py` |

**不许用**：自己发明的原语、自己估的期望值、字面 URL、`await_state(lambda …)`、用例层直调 `dialogue(`。

## 二、七步

```text
1. 查词汇：把设计条目的动作逐个在能力清单的「A. 原语」里找
   → 全找得到 → 继续；有任何一项找不到 → 走第三节，不许硬写
2. 写 marker：id / game / module / kind / title
   → 五项全部从设计条目与受控词表抄（module 只允许 shop/quest/combat/inventory/growth/minigame/craft/pet/core/known_defects）
3. 写前置：prepare(...) 的每一项对应设计条目的「前置」列
   → 若前置无法直接表达，先按第四节做只读探针，不许猜
4. 写动作：只调业务域词汇（shop/quest 模块）或 stendhal 的取数与等待原语
5. 写断言：每条 qa.check 必须带 sources.py 里的常量；
   期望值逐条来自设计条目的「预期与判据」列
6. 过门禁：python -m gameqa.hygiene（要 0 条名单外）+ pytest tests -q
7. 真机：`--case <id> --rounds 1` 看行为对不对；要验稳定性再加大 `--rounds`
   （3 轮一般就够抓偶发，轮数由你按目的定，没有"必须跑固定轮数"这条）
```

## 三、缺原语时（回流）

只允许产出一份三段式需求单，**不许绕开封装层硬写**：

```text
理由：     当前只有购买原语，出售无法在封装层内表达
缺失能力：shop.sell(player, item, qty) + NPC "Siandra" + npc_sales 观察
补齐办法：  在 src/gameqa/shop.py 增加 sell 原子；QaProbe 增加 npc_sales 读接口
```

生成期间**不许改封装层**（否则等于考试时改考纲）。

## 四、前置探针（实测结论：设计条目的"前置"经常不能直接翻译成参数）

例子：设计写"满槽 cheese3"，但**money 也占一个背包槽**（文档没写）。直接写 `prepare(items={...12 件...})` 会报 `IllegalStateException: Bag is full for money`。

做法：先写一条只读探针，跑一次，把真实状态写进 **diagnostics**，跑完从 `case.json` 读：

```python
qa.data["diagnostics"]["probe_before"] = {"bag_slots": …, "bag_full": …, "money": …}
```

**不要用"故意失败的 check"当探针**：`Evidence.check` 失败会立即抛错并中断用例，
后面的步骤根本不会执行（实测踩过：为了看动作后的状态，探针写成失败 check，结果
`case.json` 只有 1 步、动作没跑）。校准完删掉探针，再写正式用例。

## 五、三个已实测的坑

| 坑 | 现象 | 处理 |
|---|---|---|
| 前置无法直接表达 | `Bag is full for money` | 按第四节做只读探针 |
| import 来源写错／忘了导入 | 原语会在层之间搬迁（如 `leave` 从 `shop` 移到 `stendhal`）；引用一个文件里根本没有的名字时，**收集阶段看不见**（只在运行时 NameError） | 门禁两条规则静态拦：`import名字不存在`（并指出它现在在哪个模块）、`引用未定义的名字` |
| **原子签名过宽，回流可被绕过** | `confirm(player, answer)` 接受任意字符串，生成者可用它发 `sell 2 cheese`：**门禁查不出、真机全绿**（实测） | 把入口收紧成枚举（如 `answer ∈ {yes,no}`），让缺原语时结构上无法硬写 |
| **money 也是道具、占一个背包槽** | 断言"背包内容精确等于准备的道具"时，会多出一个 `money`（实测：预期 `['short sword']`、实际 `['money', 'short sword']`） | 凡断言背包内容精确相等，**必须显式设置 `money`**（`prepare(money=0, ...)` 会清掉该道具）；`money` 也参与"满槽"计算（12 槽 = 11 件道具 + money） |
| 多轮里有一轮被框架层瞬态弄脏 | 观察重试记 `unstable`（如 `inspect: no confirmed response; request was not resent`），`consistent=False` | 不是用例错，复跑一次即可；**轮数按当前目的定**，别为此固定跑多轮 |

## 六、报告口径（不许含糊）

**"重试才过"必须显式标注，不许当一次通过。**

一次运行里每条"用例 × 轮次"的观测只有三种归宿，页面与 `summary.json` 都按这个口径写：

| 归宿 | 含义 | 计入 |
| --- | --- | --- |
| `passed` 且**没有**重试标记 | 一次通过 | `first_try_passed` |
| `passed` 且**有**重试标记 | **重试才过**（先报错、基础设施抖动、重跑一次才过） | `infra_retry_count`，**不计入一次通过** |
| `failed` / `error` 且没有重试标记 | 真失败 | `unexplained_failures` |

- `infra_retry_rate = infra_retry_count / observations`（观测总数就是分母；没有观测时为 `0.0`）。
- `all_passed` 要求每条观测都 `passed` 且**没走重试** —— 所以有重试的轮次永远不会被判成全绿。
- 「结果」页的**实验**列 = 这次运行的**用途标签**（就是 `--experiment` 的值）。没人起名时的默认值：
  命令行是 **`未命名`**、面板点「执行所选」是 **`未命名-面板`** —— 看到这两个词就表示"没命名"，
  不代表谁给它起过名字。
- 运行报告页与面板「结果」页都会常驻显示一次通过与重试才过的条数；重试率 **>35% 只标黄提示，不阻断运行**
  （它是环境噪声的量化，不是用例结论 ✓）。

## 七、反例清单（出现任一项即判该条生成失败）

- 把服务端断言换成界面文字（"用户看到 60 金币"≠服务端是 60 金币）
- 期望值来自估算而不是设计条目的「预期与判据」
- 为了让用例通过而放宽断言
- 往 `hygiene.EXEMPT` 加条目或改 `EXEMPT_BASELINE`
- 缺原语时硬写而不是产出需求单
- **借用签名过宽的原子发业务指令**（如用 `confirm(…, "sell 2 cheese")` 代替出售原子）——它连门禁都查不出来，只有复核能发现
