### 回流闭环第 3 步：落地 007 / 008

**一、对上一步一处推断的更正（重要）**

B 组当时据 `bought={"cheese": 14}` 推断"`item_counter_cache` 跨用例累计、不随快照重置"。**多轮跑完后逐轮核对，该推断是错的**：

```text
每轮 preparation.before : sold={}          bought={'cheese': 14}
每轮 restoration.before : sold={'cheese': 2}   ← 动作后
每轮 restoration.after  : sold={}          ← R1 快照回滚把计数也恢复了
```

即：**计数随 R1 快照回滚**，`bought=14` 只是基线快照里本来就有的历史值。所以"写增量"的理由不是"多轮会漂"，而是：1) 设计条目要的就是"计数**增量**正确"；2) 基线不一定为零（`bought=14` 即证据），绝对值断言在基线非零时必错。`sold_count` 的 docstring 与 B 组记录里的那句话都已更正。

**二、008 的拒绝行为（探针实测）**

```text
动作 sell 2 cheese → NPC: "2 pieces of cheese are worth 10. Do you want to sell them?"
动作 yes           → NPC: "Sorry! You don't have that many pieces of cheese."
状态：money 20 不变、cheese 1 不变、sold 不变
```

三个发现：

1. **数量不足在报价阶段不校验**：报价照旧发出，只有确认之后才拒绝——所以动作序列必须按设计条目写成 `sell 2 cheese → yes`，只发到 `sell` 就断言会看不到拒绝。

3. **拒绝台词的出处无法引用官方行号**：本机检出不含该行为类（`entity/npc/behaviour/` 只有 `journal/` 子目录），外网不可达（HTTP 000）。因此该断言的出处写成"设计条目 S-BUYER + 实测观测"，并在用例的 `coverage_limit` 里**明写它的权威性弱于状态断言——锁的是当前实现，不是设计意图**。

### 查"计数增量多 1"：原来是**我读错了字段**（并牵出一个原版缺陷）

日期 2026-10-09。第 1 类问题（`ST-SHOP-API-007/009` 的计数增量期望 2/1、实测 3/2）查清了。

**现象与排除**：007 单独跑也稳定多 1；玩法事实全对（cheese 3→1、金币 20→30、只有一次成交）→ 不是多卖一次、
不是延迟写入（读完立刻是 3，1.5 秒后仍是 3）、不是基线被上一笔污染（那一次基线是**空**的）。

**根因（两个视角直接对比）**：卖 2 个 cheese 前后各读两份数据——

| 时刻 | `item_counter_cache.sold`（会话级字段） | `commerce.looted_items["sold.cheese"]`（持久真值） |
|---|---|---|
| 卖前 | `{}` | `3` |
| 卖 2 件后 | `{"cheese": 5}` | `5` |

持久值正确地 +2；而**我读的字段是从不加载的**——`PlayerLootedItemsHandler` 构造器把 `sold.*` 错装进了
`bought`（第 78 行），`sold` 永远从 0 开始。基线 0、之后"持久值+2"→ 增量看起来多 1。**是框架读错字段，不是游戏写错。**

**处置**：`sold_count()` 改为读 `commerce.looted_items["sold.<item>"]`，断言出处同步注明原因；
`ST-SHOP-API-007/008/009` 计数断言恢复（007 增量 2、009 增量 1，各 2 轮验证）。原版缺陷另立记录
（[Stendhal-003](缺陷/Stendhal-003-售出计数会话级.md)）：`Player.getQuantityOfSoldItems()` 是会话级的，
依赖它的 COMMERCE 成就在重登后会从零计。

**顺带**：`prepare` 夹具加了"在线竞态"恢复（presence 检查通过、准备时已掉线 → 重连重登 + 重试一次，
记进 `online_recovery`）；`ensure_target_online` 的异常不再无声吞掉（记进 `presence_check_errors`）。

**当前全组状态**：36 条失败 7 条，**全部是同一类**——"用例中途角色掉线"（`Target character is not online`），

### 服务端会话频掉的根因：H2 退出钩子抢跑，停服丢写（+ 洪泛阈值实测）

日期 2026-10-09。查"为什么用例随机掉线"，最后查到一个**服务端配置缺陷**，它也是之前角色被写坏、
世界不一致、不得不反复重建数据库的真正原因。

**根因（配置缺陷，已修）**：`runtime/server.ini` 的 JDBC URL 是
`jdbc:h2:.../h2db;AUTO_RECONNECT=TRUE`——**没有 `DB_CLOSE_ON_EXIT=FALSE`**。
H2 默认在 JVM 退出时关闭数据库，于是停服时它抢在 marauroa 的写队列刷完之前关掉连接：
日志里停服那一秒出现 **400+ 条** `org.h2.jdbc.JdbcSQLException: Database is already closed`
（H2 自己在报错信息里给了修法）+ 432 次 rollback + `StoreZoneCommand ... ERROR`。
后果是**每次停服都丢掉队列里没落库的写**（实测停下时队列里还有 97–197 条），
世界与角色对象因此不再自洽——这正是"角色再也登不进去 / `could not load object ... from database`"的来源。

修法：把 `;DB_CLOSE_ON_EXIT=FALSE` 加到 JDBC URL 上。落点两处（都没动上游 Java）：
`scripts/stendhal/setup.py` 生成 ini 的那一行（重建也会带上），以及现有 `runtime/server.ini` 与
`runtime-fault/server.ini` 就地修。**验证**：改前停服新增 16 条关库错误、改后**新增 0 条**，
日志显示队列刷完 → `Shutdown completed. See you later!`。

**洪泛阈值（实测）**：原服的洪泛保护在**每通道约 12 条消息/秒**就断开连接，日志原文：
`Disconnecting Channel ... for flooding server: [ time: 1 send bytes: 2137 send messages: 12 ]`
（`allowed_messages_per_second` 那个 1024 是缓冲区常量，不是阈值）。
已在 `Bridge.call` 加**每连接最小请求间隔**（默认 0.18s，约 5.5 条/秒）；`await_state` 本身已有 0.3s 间隔。
一轮 36 条的洪泛断开从"多次"降到 **1 次**（剩余那次可能是模拟器侧客户端造成的，未进一步区分）。

**顺带发现：登录限流**。一轮全失败（36 条都是"Server rejected character"）之后，bootstrap 报
`Login failed: There have been too many failed login attempts for your account or network`。
该记录**存在数据库里**（重启不清），且**每次失败重试又记一笔**，会自我维持；处理办法是换一个空库并**立刻** bootstrap。

**环境处置**：角色损坏（修复前的丢写造成的累积损坏）→ 又重建两次数据库，
留档 `database-broken-20261009T182518`、`database-throttled-20261009T183807`。

**当前状态**：全量 API 36 条 —— 非基础设施失败 **1**（`ST-BAG-API-007-heal`）、基础设施重试 **6**（约 17%）、
关库错误 **0**；门禁 0 违规、自检 55 passed。
**下一步**：① 查 `ST-BAG-API-007-heal` 那次不属于抖动签名的错误；② 把剩余的抖动（17%）继续压下去，
重点是洪泛与登录限流的交互；③ 给框架加一条"检出登录限流就停下"的保护，避免全组空跑。

### 查"不属于抖动签名的错误"：两个都是我自己的判定缺陷

日期 2026-10-09。上一节留下的 `ST-BAG-API-007-heal`（判 `error` 但它 10 步全过）查清了，顺带修掉一处判定不一致。

**缺陷一：自愈成功却留下假失败标记。**
`Stendhal.prepare` 在 `_guarded("prepare")` 抛出任何非"快照已存在"的错误时，**先**落
`failure_kind = preparation_error`。实测序列：prepare 撞上 `TimeoutException` → 记下标记 → 夹具的在线自愈
把角色重新拉上线、**重试成功** → 用例 10 步全部通过 → 但没人清那个标记，插件据它把整条判成 `error`
（`phases` 里 setup/call/teardown 全是 passed）。修法两处：抖动签名（`bridge.is_infrastructure_error`）
导致的准备失败**不落**该标记；夹具自愈成功后再兜底清一次。签名表移到 `bridge.py` 由运行器与封装层共用。

**缺陷二：重试判定多了一道 outcome 门。**
`infra_failed` 原来要求 `outcome == "error"`；而抖动落在**用例体内**时会被记成 `failed`，
于是 `ST-SHOP-API-005-negative` 的失败文本明明写着 `IndeterminateAction: prepare: TimeoutException`
却不被重试。改为**只看签名**（业务断言的文本里没有这些签名，所以照样不重试），单测固定这条边界。

**`ST-SHOP-API-009` 是真实失败（不是环境）**：NPC 已报价 40、`yes` 也发出去了，但金币一直没扣
（等了 5 秒仍是 100）——那次业务动作**丢了**（发送时连接正在断）。按裁定不重放业务动作，所以这条**理应失败**。
更好的写法是断言 NPC 对 `yes` 的回复（一个明确的结算点），这样"回复没到"本身就是证据——留作下一步。

自检 55 → **57 passed**；门禁 0 违规。当前全量：非基础设施失败 1（就是上面这条 009），基础设施重试约 25%。

### 压抖动：洪泛/GC/登录 churn 逐一排除，补上宠物与"失败即回收"

日期 2026-10-09。继续追那 ~28% 的抖动，做了四个对照实验，否掉三个假设，并修掉两个真实缺口。

**① 洪泛不再是主因（对照实验）**：把框架限速关掉、在一个连接上突发 30 次 `inspect`——
实测**没有**洪泛断开，而是第 4 个请求**卡了 11 秒然后超时**（≈0.3 请求/秒）。也就是说剩下的掉线
主要是**服务端间歇性僵住十几秒**，不是洪泛。（洪泛阈值仍是每通道约 12 条/秒，保持 0.18s 限速。）

**② GC 排除**：在突发请求的同时用 `jstat -gc` 采样服务端——**0 次 Full GC**、累计 GC 仅 0.945 秒（94 次 young）。
堆使用在 170–200MB 之间正常波动。GC 不是原因。

**③ 登录 churn 排除**：把角色会话改成整轮复用后，登录次数 36 → 1~6 次、耗时 478 → 433 秒，
但**抖动率没变**（仍 10 条重试）——假设被否。而且共享会话移除了一个**意外的状态重置**：
以前每条用例重新登录会从数据库重载角色，顺手抹掉了未落库的运行期状态；共享后暴露出两个真实泄漏
（宠物羊、HP/atk_xp）。既然复用对抖动毫无帮助，**已回退**（并在夹具注释里写明原因与前置条件）。

**④ H2 调优**：`jdbc_url` 加 `;WRITE_DELAY=500;CACHE_SIZE=131072`（减少同步刷盘压力）。

### 停顿看门狗（jstack），以及"服务端日志干净但仍抖动"的定位

日期 2026-10-09。给桥加了**停顿看门狗**：任何桥请求超过 3 秒（或超时）就自动 dump 服务端 `jstack`。

实现（`src/gameqa/bridge.py`）：
- `Bridge(..., server_log=...)` 由夹具传入；`server_pid()` 从 `server.pid` 解析（runtime 下，也兼容 log 同级），
  `jstack_binary()` **按顺序探测**候选并排除 macOS 自带的占位符——`/usr/bin/jstack` 在没有 Java 的机器上
  只会打印 `Unable to locate a Java Runtime`，必须用**跑服务端的那个 JDK**（版本也要匹配）。
- 慢请求与超时两条路径都会 dump；**限频 10 秒、整轮最多 20 份**；文件写到 runtime 下的 `qa-stalls/`
  （不污染仓库），路径记进 `diagnostics.stall_dumps`。

**冒烟验证**：dump 出 52 个线程 / 37KB，能直接读到线程状态（`marauroad` 在 `Object.wait0`、`NioServer` 在
`KQueue.poll`、`RPServerManager` 在 `Thread.sleep0`）。

**整组实测（关键结论）**：一轮 36 条里**没有触发一次 dump**——说明这一轮的抖动**不是**"请求慢过 3 秒"，
而是**瞬时连接失败**。同时段服务端日志：`is flooding: 0`（最后一次洪泛在 18:42，**限速之后已归零**）、
`ERROR: 0`；只有两条预期内的业务 WARN（拒绝卖 1001 个 cheese、`buy -1 cheese` 解析）。
即：**服务端在运行期是健康的、什么都不报**，但客户端仍会遇到写失败 —— 最可能是服务端的 selector 循环
被某个较长 tick 占住（接收窗口满，客户端写阻塞后自身超时），这类"软停顿"不足 3 秒，看门狗按当前阈值抓不到。

**下一步（若要继续压那 ~25%）**：把阈值降到 1.5 秒（相应把限频放宽到 5 秒），或者在服务端加一个
"tick 超过 X 毫秒就记录"的采样；两者都能把"软停顿"的时间点与栈抓下来。

### 1.5 秒阈值仍然抓不到：抖动是瞬时 RST，不是慢请求

日期 2026-10-09。把看门狗阈值降到 1.5 秒（限频 5 秒、上限 40 份）再跑一整轮：
**36 条里一次 dump 都没有** —— 也就是说**没有任何一个请求慢过 1.5 秒**。抖动全是**瞬时**的。

据此把机制缩到最窄：
- 客户端侧错误是 `IOException`（对端关闭/重置），**没有**桥进程崩溃迹象（无 OOM/hs_err/bridge exited）；
- 服务端侧**什么都没记**：`is flooding` = 0、`ERROR` = 0、`Request (*)  disconnection of Player` 全量只有 1 次（凌晨 03:10 的 TIMEOUT），
  也没有重复登录踢人（`Logged out because`/`already logged in` = 0）；
- 网络路径上有一段**项目本地补丁** `integrations/stendhal/network_patch/NIONetworkConnectionManager.java`
  （`setup.py` 会编译它并覆盖原版）。它第 195-215 行是：`if (floodValidator.isFlooding(channel, count)) { warn; onFlood(channel) }
  else { queue.put(...) }` —— **只有判定"没洪泛"才把消息入队**，判定为洪泛就关连接并且**丢弃这条数据**。
  这个设计很脆：任何一次误判都会静默丢一条消息并断开，而唯一的痕迹是一条 WARN（本窗口里没有）。

**下一步（要收口这三条之一）**
1. 用 `tcpdump -i lo0` 在跑用例时抓一次 FIN/RST 的方向，确认是服务端主动关还是客户端；
2. 审这段 NIO 补丁：把"洪泛"分支改成先记录（含字节数/消息数）再决定，或让误判不至于丢掉整条消息；
3. 若确认是 marauroa NIO 层静默关闭，就在关闭路径上补一条带原因的 INFO 日志（类似它已有的 `Request (*) disconnection`）。

现状不变：全量 API **非基础设施失败 0**、基础设施重试 8~9 条（≈25%，全部被重试吸收）、门禁 0 违规、自检 57 passed。

### FIN 方向定了：服务端先关；并测出"静默 10–15 秒即被关"与"同账号重复登录静默踢人"

日期 2026-10-09。用无需 root 的办法判方向（`tcpdump` 在 macOS 上要 root，本会话不能提权）：
以 0.3 秒粒度轮询 `netstat -an -p tcp` 里 loopback:32160 的连接状态，跑一整轮。
判据：`CLOSE_WAIT` 表示**收到**对端 FIN，`FIN_WAIT_*` 表示**自己先发** FIN。

**结果（199 次半关状态，一一对应）：服务端先发 FIN = 199，客户端先发 FIN = 0。**
即**服务端主动关掉我们的连接**，而它不写任何原因（无 flooding WARN、无 ERROR、无 TIMEOUT、无 kick 关键字）。

**第二个决定性测量：静默容忍只有 ~10–15 秒。** 登录后什么都不发，再发一个请求：
8 秒 ✓ 可用；**15 秒 ✗ 连接已被关**（`IOException`）；25 秒 ✗ 角色已判定离线。
这解释了为什么限速/洪泛/GC/登录 churn 都不是主因：桥只在框架要操作时才说话，
长等待（UI 走路时观察者闲着、长 await、用例之间的空隙）就会被关。

**因此加了保活**（`Bridge(keepalive_op=..., keepalive_args=..., keepalive_interval=5.0)`）：
登录成功后起一个守护线程，静默超过 5 秒就发一次只读保活；夹具传 `presence`（观察者）与
`get_chat_messages`（角色）。**部分验证**：开着保活静默 20 秒仍可用（关掉时 15 秒就死），
但 40 秒时仍失败、且线程在首次失败后自己退出了 —— 说明选的两个操作很可能**由桥在本地作答**，
根本没上服务端；需要换一个**确实走服务端**的只读操作，并让线程失败后继续重试而不是退出。

**顺带发现的第三个机制：同一账号重复登录会静默踢掉前一个会话。** 三个并发观察者登录实验里，
后两个的 `login` 直接 `IOException`——而服务端日志里找不到任何"kicked/logged out because"记录。
这条要纳入嫌疑：每条用例都会登录/登出角色与观察者，如果上一条会话的断开**晚于**下一条的登录被处理，
就可能把**新**会话当成旧会话移除（这能解释"瞬时失败、服务端无日志、约 25% 概率"）。

**现状**：全量 API 非基础设施失败 0~1、基础设施重试 8 条（≈22%）、门禁 0 违规、自检 57 passed。
**下一步**：① 单独（不要并发）测出哪个保活操作真的过服务端，并把保活线程改成失败后继续；
② 验证"登录踢人"这条：用例结束时等一条 `NET Disconnecting` 再让下一条登录（或把会话复用重新评估）。

### 保活落地（含失败后重试），并定出剩下的唯一嫌疑

日期 2026-10-09。

**保活最终形态**：`Bridge(keepalive_op=..., keepalive_args=..., keepalive_interval=5.0)`，登录成功后起守护线程，
静默超过 5 秒发一次保活；**失败不再退出**（首版首次失败就 return，导致保活悄悄失效——实测 40 秒照样被关），
现在会按节奏继续重试并累计 `keepalive_sent`/`keepalive_errors`。观察者的保活操作用 **`inspect`**：
它读的是目标的实时状态，一定是服务端往返（`presence`/`get_chat_messages` 可能由桥在本地作答）。

**测量结论（两条，都硬）**
1. **静默容忍 ~10–15 秒**：登录后什么都不发——8 秒可用、15 秒连接已被关、25 秒角色已判定离线。
   保活开着时静默 20 秒仍可用（不用保活 15 秒就死），说明保活确实在续命。
2. **同一账号重复登录会静默踢掉前一个会话**：三个并发观察者登录时，后两个 `login` 直接 `IOException`；
   随后一次自己的测试脚本里，新登录的角色会话也被"晚到的旧会话断开"移除（连报两次）。
   服务端日志里**找不到**任何 kicked/logged out because 记录——所以之前"0 次踢人"的 grep 是关键字不对。

**但整组抖动没有下降**（保活前后都是 8~11 条重试，真失败 0）。因此**组内那 ~25% 不是（或不只是）静默超时**，
而是更像上面第 2 条：每条用例都登录/登出角色与观察者，上一条会话的断开若晚于下一条登录被处理，
就会把**新**会话当成旧会话移除——这正好解释"瞬时失败 + 服务端无日志 + 约 25% 概率 + 只在组内出现"。

**下一步（唯一嫌疑，方案已明确）**：给登录加一个"确认自己是当前会话"的握手——
登录后立刻发一次只读操作并校验目标在线；若被踢则重登一次（现在框架只在 `prepare` 失败后才自愈，
登录本身没有校验）。或者改为**按账号复用会话**并在这条会话上做同样的自校验。

### 登录自校验握手：已落地（本轮未触发，说明掉线发生在用例中途）

日期 2026-10-09。在 `prepare` 夹具里加入握手：每次准备前用 `observer._guarded("inspect", read_only=True)`
（一定过服务端）确认目标在线，也就是确认"我这条登录才是当前会话"；不在线就重登并**退避重试**（1.5/3/4.5 秒），
记录进 `diagnostics.login_handshake`。动机是"同账号重复登录静默踢人"那条机制。

**整组实测**：基础设施重试 **7 条**（此前 8~11 条，是最好的一次），**非基础设施失败 0**；
但**握手一次都没触发**（`login_handshake` 为空）——说明每次准备时目标都在线。
结合"静默 10–15 秒即被服务端关连接"那条测量，掉线是发生在**用例中途**，而不是准备之前。

**由此收窄到最后一个具体动作**：观察者的保活已经用 `inspect`（有效），但**角色侧的保活操作
`get_chat_messages` 很可能由桥本地作答**（没上服务端），所以角色的会话在长步骤里照样被关；
角色掉线的后果就是之后所有观察者读取都报 `Target character is not online`。
下一步很明确：给角色侧也找一个**确实过服务端**的保活（或干脆在空闲超过约 10 秒后，动作前先重登一次角色）。
握手保留：它是廉价的安全网，且已验证不会误伤（本轮 0 次触发、0 副作用）。

### 模拟器输入法：让中文输入彻底不参与（并固化进 connect.sh）

日期 2026-10-10。用户要求"删除模拟器中的中文输入法"。查证后的事实：

- **没有独立的中文输入法包可删**：`pm list packages` 里与输入法相关的只有 Gboard
  （`com.google.android.inputmethod.latin`）、TTS 语音输入和一个 Airtest 自带的注入 IME
  （`com.netease.nie.yosemite/.ime.ImeService`）。"中文输入法"其实是 **Gboard 内建的中文/拼音语言包**，
  随 APK 一起发行，删不掉。
- 所以做法是**让它不参与输入**，两步：
  1. **清掉 Gboard 的中文数据**（`pm clear`）→ 中文子类型归零（实测 `ime list -a` 里 zh/pinyin 命中 0）。
  2. **把默认输入法切成 Airtest 自带的注入 IME**（`ime set com.netease.nie.yosemite/.ime.ImeService`）→
     自动化打字完全绕开 Gboard，候选区再也不会吞掉 `text()`。
- **固化**：两步都写进 `scripts/android/connect.sh`，每次连模拟器时重申（谁把它切回 Gboard 也会被自动纠正）。
  实测：故意切回 Gboard → 跑一次 `connect.sh` → 默认输入法回到注入 IME、中文子类型仍为 0。
- **实测收益**：`ST-SHOP-UI-001` 通过且 **`unstable=False`**（此前 Gboard 时代会有一次"用户名框未命中后重试"），
  用户名 `qaplayer` 一次落进输入框。
- 文档：`docs/环境部署.md` 第 4 节记明"必须重申输入法"及原因（不这么做 UI 用例必然卡在登录步骤）。

### 修偶发：跑完用例立刻跑自检必红 2 条

日期 2026-10-10。规律是：**刚跑完一条用例就立刻跑 `pytest tests`**，`tests/test_pytest_report.py` 里两条
会以 `returncode=4` 失败，输出 `ERROR: 已有测试、角色清理或健康检查在进行，请等待结束后再试。`
原因：这两条测试会**起内层 pytest**，而内层 pytest 经 `pytest_plugin` 会自己取共用运行锁；
面板的健康检查或刚结束的任务可能还占着锁 → 内层直接以 UsageError 退出 4 → 与被测的业务语义无关。
面板的「跑框架自检」按钮正好会踩这个。

修法（测试侧，最小改动）：加 `run_inner_pytest(project, extra, env=None)` 封装，
输出里出现"已有测试"就等 5 秒重试，最多 4 次；两处内层调用改用它。
验证：先跑 `ST-SHOP-API-001`（passed），**立刻**跑自检 → 97 passed（此前必红 2 条）。
